### ★ 转移通路（2026-09-12 修好，双向实测通过）

**两个方向都已实测通过**（使用者 2026-09-12 确认）：游戏 → IA（拾取）与
IA → 游戏（转移）都通。

`POST /api/items/transfer`，请求体 `{ ids: number[], transferAll: boolean }`，
`ids` 是 `PlayerItem.Id`。响应 `{ success, numTransferred, failed }`。

- C# 侧把 id 拼成 `["PI", id, "", "", "", false]` 的 identifier 交给
  `ItemTransferController`，**与旧 WebView2 路径调用的是同一个控制器**。
- 它做两件事：把物品序列化成 CSV 写进 `CsvLocationOutgoing`（**不是直接写存档**），
  由注入游戏的 hook 读取后放进共享仓库；然后把 `StackCount` 置 0 由 `Update` 删记录。
- ⚠️ **失败时也返回 HTTP 200**（`{success:false, error:"…"}`）。
  前端必须判 `success` 字段，只看 `res.ok` 会把"转移失败"显示成"已转移 0 件"。
- ⚠️ 「转移到任意 Mod」会让控制器弹 `StashPicker` 模态框，必须跑在 UI 线程上；
  HTTP 请求在线程池线程，所以**开启该设置时 HTTP 转移直接返回明确错误**，不会半路崩。
  （这是"旧界面功能没补齐前不能删 WinForms"的一个具体例子 → B5/B6。）

### ★ 列表刷新（B2 已落地）

后端有 WebSocket 了：`ws://127.0.0.1:3031/ws`，**服务端 → 客户端单向推送**。
数据库一变（游戏里捡到物品、转移走物品、重新解析游戏数据、改了 `hideSkills`），
C# 就广播一条 `{ "type": "itemsChanged" }`，页面自己用 REST 重查当前列表。

- 帧格式：**只发轻量信号，不带数据**。理由见
  `IAGrim/Http/WebSocketHub.cs` 的类注释与 `05-实施计划.md` §6。
- 广播点：`MainWindow` 的 `_csvParsingService.OnItemLooted`（拾取）、
  `ListviewUpdateTrigger` / `DatabaseLoadedTrigger`，以及 `WebServer` 里
  HTTP 转移成功之后。
- ⚠️ **别挂错地方**：拾取物品走的是 `OnItemLooted`，**不是** `ListviewUpdateTrigger`
  （后者是设置变更时用的）。两条路都已实测。
- 前端 `connectLive()` 自动重连（500ms 起翻倍，上限 15s）。

**轮询降级仍在，但只在 WS 断开时启用**：`App.tsx` 里若 `live === false`，
才退回"每 4 秒比较 `total`"。另有窗口重获焦点时刷新、标题栏「刷新」按钮。
后端重启或浏览器断线时界面不会变成死数据。

> ⚠️ 已知限制：改动**已有**物品（属性重算、改名）不会触发广播——
> 现在只有"增/删物品"这类会走 `OnItemLooted` 的路径才推。

   要用 PowerShell 发请求 → `04-开发环境.md` §9.4
3. **跑 Debug 还是 Release**：Debug 用隔离的 `userdata-test.db`（空库），
   验证真实数据要用 **Release** → `04-开发环境.md` §9.5
4. **不能从 UNC 路径运行 exe**：`\\wsl.localhost\...` 会**静默失败**，
   要复制到 Windows 本地再跑 → `04-开发环境.md` §9.6
5. **改前端后要手动拷进 storage**：`rm -rf storage/assets && cp -r WebUI-next/build/. storage/`
