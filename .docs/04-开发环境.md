## 1. 环境规划

**计划中的主要开发环境：Windows 主机 + WSL2。**

```
┌───────────────────────────── Windows 主机 ─────────────────────────────┐
│  · .NET 10 SDK（编译 IAGrim，命令行 dotnet build）                      │
│  · VS Code + C# Dev Kit（写 C#、调试）                                  │
│  · WebView2 Runtime（过渡期需要，改造后不再需要）                        │
│  · Grim Dawn（游戏本身）                                                │
│  · 浏览器（开发调试 / 打开程序界面）                                     │
├───────────────────────────── WSL2 ─────────────────────────────────────┤
│  · VS Code + Remote-WSL                                                │
│  · Node.js 20 LTS / npm                                                │
│  · git                                                                 │
└────────────────────────────────────────────────────────────────────────┘
```

### 1.1 一个需要注意的坑：仓库放在哪个文件系统

WSL2 访问 Windows 盘（`/mnt/c/...`）是**跨文件系统**的，大量小文件读写很慢；
反之 Windows 程序访问 WSL2 的文件系统（`\\wsl$\...`）也有兼容与性能问题。

`node_modules` 动辄几万个小文件，放在 `/mnt/c` 下 `npm install` 会明显变慢。

**三种可选做法：**

| 做法 | 说明 | 评价 |
|---|---|---|
| A. 仓库放 Windows 盘，**前端也用 Windows 版 Node** | 不经过 WSL2，所有文件都在原生文件系统 | ✅ **最省事**，若不需要 Linux 工具链就选它 |
| B. 仓库放 Windows 盘，前端用 WSL2 的 Node | VS 能正常打开；`npm` 走 `/mnt/c`，较慢 | ⚠️ 可用，但安装依赖慢 |
| C. 仓库放 WSL2 文件系统 | npm 快；但 Windows 上的 VS 打开 `\\wsl$` 路径体验差 | ❌ 不推荐，C# 侧要编译 |

> **建议**：先用 A（Windows 原生 Node），遇到需要 Linux 工具的场景再切 B。
> WSL2 的价值主要在命令行工具链，而前端构建本身不依赖 Linux。

## 3. 开发工作流

### 3.1 只改前端（最常见）

```bash
cd WebUI
npm install        # 首次
npm run dev        # Vite 开发服务器，默认 http://localhost:3000
npm run lint       # 代码检查
npm run build      # 产出到 build/
```

浏览器打开开发服务器即可调试。

**现有前端的特殊情况**（过渡期）：此时 `isEmbedded === false`，部分数据走 `src/mock/` 的假数据
（界面上会出现"加载 mock 物品"按钮，仅开发模式显示），搜索与物品转移不可用。
**纯布局/样式工作完全够用。**

**新前端没有这个限制**（见 §3.2）——它本来就是给浏览器用的。

### 3.2 新架构下的开发方式（目标形态）

新前端就是一个普通的 Web 应用（浏览器访问），所以开发流程也是标准的：

```bash
npm run dev          # 1. 起 Vite 开发服务器
```
```
vite.config.ts       # 2. 把 /api 代理到 C# 的本地服务（server.proxy）
```
3. 浏览器打开 → 改代码即时热更新 → 需要真实数据时经代理拿到

**这比现在舒服得多**：开发时的形态和发布时的形态几乎一致，
不需要 WebView2、不需要打包、不需要重启主程序。

> **过渡期怎么办**：改造完成前，现有前端仍按旧方式工作（见 §3.1 与 §3.3）。
> 两条路可以并存。

### 3.3 完整构建（要出成品时）

```bat
cd WebUI
build.cmd          REM = fnm use + npm run build + xcopy 到 IAGrim 的 Resources
```
然后在 Visual Studio 中构建 `IAGrim-core.sln`。

`build.cmd` 的两个细节：
- 产物目标路径含 `win-x64`：`IAGrim/bin/{Debug,Release}/net10.0-windows/win-x64/Resources`
- 会先删除目标目录里旧的 `assets/`（文件名带内容哈希，不清会堆积）

## 5. 常见坑

| 现象 | 原因 / 对策 |
|---|---|
| 以为要用 Visual Studio | 不需要。装 .NET SDK + VS Code 的 C# Dev Kit 即可 |
| 编译报 `CS0246 AutoUpdaterDotNET` | 缺 `AutoUpdater.NET.dll`，见 `README.md` |
| 程序启动报缺少 WebView2 Runtime | 装 Evergreen Runtime（过渡期需要，改造后不需要） |
| 浏览器里没有物品 | 现有前端：正常，点"加载 mock 物品"按钮。新前端：检查 `/api` 代理配置 |
| 浏览器里文字是英文 | 正常：中文文案由游戏汉化包提供（后端读取），前端内置的降级文案就是英文 |
| 物品图标全是占位图 | 需要把游戏图标放进 `WebUI/src/static/` |
| `npm install` 很慢 / 失败 | 检查仓库是否在 Windows 盘却被 WSL2 访问（见 §1.1）；或网络问题 |
| 改了 CSS 在旧程序里没生效 | 说明用的是打包页面而非 dev server |
| 想跑 `dotnet build` 但命令不存在 | 需要在 Windows 上装 .NET 10 SDK |
