## 1. 环境拓扑（实测）

**核心决策：agent 与仓库都留在 WSL2，Windows 只承担编译与运行。**

```
┌────────────────── Windows 主机 ──────────────────┐
│  · .NET 10 SDK            ⚠️ 待安装（当前只有 Runtime，见 §2）│
│  · Grim Dawn + IA 安装目录（游戏本体、图标资源来源）        │
│  · 浏览器（调试前端、打开程序界面）                       │
│  · C++ 工具链 —— 仅当要改 HookDll 时才需要               │
├────────────────── WSL2 · Ubuntu 24.04 ───────────┤
│  · ★ 仓库：/home/jyl/iagd      ← ext4 原生文件系统      │
│  · ★ agent（DSH）             ← bash/glob/grep 都在此执行 │
│  · VS Code Server + Remote-WSL                      │
│  · Node.js / npm / git / python3                    │
└──────────────────────────────────────────────────┘
```

### 1.1 为什么这样切分

按重要性排序，三条理由：

1. **agent 的工具链主路径是 Linux。** agent 的 bash / glob / grep / 沙箱机制是在 Linux 上训练出来的主路径；在 Windows 原生上改用 PowerShell 属于长尾能力，模型容易犯 Linux 肌肉记忆的错（路径、引号、编码、行尾）。这个坑到 2026 年仍未消失——同期 Claude Code 仍有
   [#51788](https://github.com/anthropics/claude-code/issues/51788)（设了 `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` 仍默认调 bash 工具）、
   [#45831](https://github.com/anthropics/claude-code/issues/45831)（默认吐 bash/Unix 语法）这类问题。
2. **工作量最大的一侧不依赖 Windows。** 线 A（新前端）与线 C（界面迁移，**工作量最大**）都是纯 Web 工作。目标架构把后端变成 HTTP 服务后，前端开发完全不需要 Windows。
3. **跨边界只发生在"编译这一刻"。** 编译读的是几百个 `.cs` + DLL 引用，不是几万个小文件；而 `npm install` 那种几万个小文件的操作，全部留在 WSL 原生文件系统上，不过 9p 边界。

一句话：**让 agent 待在它的母语环境里，让 Windows 只做它独占的事（编译 Windows 目标、跑游戏、开浏览器）。**

### 1.3 仓库位置：留在 WSL，不搬

**决策：仓库保持 `/home/jyl/iagd`，不搬到 Windows 盘。**

理由：

- **agent 是日常主力**，仓库在哪它就在哪干活。放在 `/mnt/c` 会让每次 `grep`/`glob`/`git`/`npm` 都过跨文件系统边界——315 个 `.cs` 还扛得住，`node_modules` 的几万个小文件会明显拖慢，而 npm 正是前端主力工作流。
- **跨边界编译的代价更小。** `dotnet build` 读的是几百个 `.cs`，量级远小于 `node_modules`。把开销放在编译这一刻，比放在每次文件操作上划算。
- **改主意的成本很低。** 仓库在 git 里，本来就"每步改动都提交"，真想搬就是一次 `clone`。

> **什么时候该重新考虑**：如果线 B/C 变成高频迭代（后端编译一天几十次），或实测 `dotnet build` 走 `\\wsl.localhost` 超过一两分钟。
> 那时的备选是"WSL 主力 + Windows 盘再 clone 一份、用 git 同步"——两边都是原生文件系统，代价是多一步 pull。

## 2. 前置条件：装 .NET 10 SDK

> ⚠️ **这是当前阻塞后端工作的第一件事。**

实测 Windows 上**只有运行时，没有 SDK**：

```
C:\Program Files\dotnet\
├── dotnet.exe
├── host/
├── shared/           ← 只有运行时（NETCore.App 10.0.12 / WindowsDesktop.App 10.0.12）
└── （无 sdk/ 目录）
```

因此 `dotnet build` 的实际报错是：

```
No .NET SDKs were found.
```

**做法**：从 <https://dotnet.microsoft.com/download/dotnet/10.0> 装 **SDK x64**（不是 Runtime）。

装完验证：

```bash
dotnet --list-sdks      # 应出现 10.0.x
```

**不需要 Visual Studio。** SDK 自带 MSBuild；唯一缺的是 WinForms 可视化设计器，而本项目的方向恰恰是**不用 WinForms**。

## 3. 跨边界：从 WSL 使用 Windows 工具

### 3.1 UNC 路径的坑（实测）

WSL 里的 `/home/jyl/iagd`，在 Windows 看来是 UNC 路径：

```
\\wsl.localhost\Ubuntu-24.04\home\jyl\iagd
```

而 **`cmd.exe` 不支持 UNC 路径作为当前目录**。直接 `cd` 过去会**静默退回 `C:\Windows`**，
只打印一段警告（GBK 编码，在 WSL 里显示为乱码）：

```
CMD.EXE 不支持 UNC 路径作为当前目录，默认值设为 Windows 目录。
```

命令看起来执行了，实际在**错误的目录**里——这是最危险的一类坑。

**解法：用 `pushd`**（它会临时映射一个盘符，实测映射为 `Z:`）：

```bash
cd /mnt/c && cmd.exe /c 'pushd \\wsl.localhost\Ubuntu-24.04\home\jyl\iagd && <你的命令> && popd'
```

实测 `pushd` 之后 `cd` 输出 `Z:\home\jyl\iagd`，并能正确列出 `IAGrim-core.sln` ✅

> **开头的 `cd /mnt/c` 是必须的。** `cmd.exe` 的*初始*工作目录由 WSL 传入（UNC 形式），会在启动时先打印那段警告。先切到 Windows 可见的目录，输出就干净了。
> 另外 `cmd.exe` 已在 PATH 中（`/mnt/c/Windows/system32/cmd.exe`），不必写绝对路径。

### 3.2 编译命令

```bash
cd /mnt/c && cmd.exe /c 'pushd \\wsl.localhost\Ubuntu-24.04\home\jyl\iagd && dotnet build IAGrim-core.sln && popd'
```

**关于 C++ 项目**：`IAGrim-core.sln` 里**只有 7 个 C# 项目**
（`IAGrim` / `Parser` / `DataAccess` / `StatTranslator` / `Cloud` / `EvilsoftCommons` / `DllInjector`），
**不含任何 `.vcxproj`**。所以这条命令**不需要 MSVC**。
`HookDll` 与 `injectAllTheThings` 的 C++ 工程独立于该解决方案，只有要改注入 DLL 时才需要在 Windows 装 C++ 工具链。

## 4. 日常工作流程

### 4.1 纯前端开发（最常用）

全在 WSL 内完成，**完全不碰 Windows**：

```bash
cd ~/iagd/WebUI
npm install          # 首次
npm run dev          # → http://localhost:3000
npm run lint         # 代码检查
```

浏览器（Windows 侧）直接打开 `http://localhost:3000` —— **WSL2 自带 localhost 转发**。

现有前端在浏览器里跑时 `isEmbedded === false`，走 `src/mock/` 假数据分支，
**纯布局/样式工作完全够用**（界面上的"加载 mock 物品"按钮仅开发模式显示）。

> WSL 没装 fnm，也不需要——`npm run dev` 直接调用 WSL 的 Node，不走 `.node-version`。

### 4.2 后端编译

```bash
cd /mnt/c && cmd.exe /c 'pushd \\wsl.localhost\Ubuntu-24.04\home\jyl\iagd && dotnet build IAGrim-core.sln && popd'
```

加 `-c Release` 可出 Release；`--no-restore` 可跳过还原，加快增量构建。

### 4.3 把前端产物送进运行目录

`WebUI/build.cmd` 是 Windows 批处理，**在本方案下有两个问题**：

1. 第一行 `fnm use` —— WSL 没装 fnm；
2. 末尾有 `pause` —— **agent 调用会永久挂住**（这是硬性禁止项，见 §4.5）。

WSL 等价流程：

```bash
cd ~/iagd/WebUI
npm run build

RES=~/iagd/IAGrim/bin/Debug/net10.0-windows/win-x64/Resources
rm -rf "$RES/assets"        # 文件名带内容哈希，不清会越积越多
cp -r build/. "$RES/"
```

> **顺序很重要**：先 `dotnet build` 生成 `bin/`，再拷前端产物。
> `bin/` 不存在时无处可拷——这是全新 checkout 上第一次构建最容易踩的坑。

输出路径里的 `win-x64` 来自 `IAGrim.csproj` 的 `<RuntimeIdentifier>win-x64</RuntimeIdentifier>`。

### 4.4 完整构建（要出成品时）

1. **编译后端** → 生成 `bin/`（§4.2）
2. **构建前端并拷贝** → `npm run build` + `cp`（§4.3）
3. **要 Release** → 把 §4.3 路径里的 `Debug` 换成 `Release`，并 `dotnet build -c Release`
4. 产物在 `IAGrim/bin/{Debug,Release}/net10.0-windows/win-x64/`

### 4.5 agent 的工作方式 ★

- agent 在 **WSL** 里，所有 `bash` / `glob` / `grep` / 文件读写都在 WSL 原生侧执行，工具语义与性能都是最佳状态。
- **后端编译由 agent 自己经 interop 闭环**，使用者不需要切到 Windows 手动敲命令：agent 执行 §4.2，就能看到真实编译结果并据此修正代码。
- **文件沙箱**：`/home/jyl/iagd` 可写；仓库之外只读。这意味着 agent 不能改写 Windows 盘的任何东西——若将来需要，要显式放宽策略。
- **铁律：不要调用 `WebUI/build.cmd`**（`pause` 会挂住 agent 的 shell）。用 §4.3 的 WSL 流程代替。
- **不要让 agent 在 `/mnt/c` 下做批量文件操作**：跨文件系统慢，且 `node_modules` 量级会放大这个问题。

### 4.6 git

仓库在 WSL，git 操作全部在 WSL 侧。实测：

- **没有 `.gitattributes`**
- **没有设置 `core.autocrlf`**（local / global 均未设）

当前无碍，因为 Windows 侧不参与 git 操作。⚠️ 若将来 Windows 侧也要 `commit`/`checkout`，
**先加 `.gitattributes` 固定行尾**，否则可能引入 CRLF 污染。

## 6. 常见坑

| 现象 | 原因 / 对策 |
|---|---|
| 以为仓库在 Windows 盘 | **实测在 WSL ext4**（`/home/jyl/iagd`）。这是有意选择，见 §1.3 |
| 以为 agent 跑在 Windows 上 | **实测 agent 在 WSL 内**，bash 工具即 WSL 的 bash |
| `dotnet build` 报 `No .NET SDKs were found` | Windows 只装了 Runtime。装 **.NET SDK 10.0**，见 §2 |
| 跨边界命令"执行了但没效果" | cmd.exe 的 UNC 限制导致静默退回 `C:\Windows`。用 `pushd` + 前置 `cd /mnt/c`，见 §3.1 |
| **agent 卡住不返回** | 很可能调了 `WebUI/build.cmd`，末尾 `pause` 会永久等待。改用 §4.3 的 WSL 流程 |
| `bin/` 目录不存在，前端产物无处可拷 | 先 `dotnet build` 生成 `bin/`，再拷前端，见 §4.3 |
| `npm install` 很慢 | 检查仓库是否跑到了 `/mnt/c` 下。应保持在 WSL 原生文件系统 |
| 改动前端后旧程序界面没变 | 用的是打包页面而非 dev server；或忘了 §4.3 的拷贝步骤 |
| 浏览器里没有物品 | 现有前端：正常，点"加载 mock 物品"按钮；新前端：检查 `/api` 代理配置 |
| 浏览器里文字是英文 | 正常：中文文案由游戏汉化包提供（后端读取），前端内置降级文案是英文 |
| 物品图标全是占位图 | 需要把游戏图标放进 `WebUI/src/static/` |
| 编译报 `CS0246 AutoUpdaterDotNET` | ⚠️ 上游文档提到，但实测 `csproj` 无此引用。若真遇到，见 `README.md` |
| Node 版本不一致 | `.node-version` 写 v20，WSL 实际 v22.23.2。⚠️ 若 Vite 报版本问题，用 fnm 对齐到 v20 |
| 以为要用 Visual Studio | 不需要。装 .NET SDK 即可 |
