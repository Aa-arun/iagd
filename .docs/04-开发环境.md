## 1. 环境拓扑（实测）

**核心决策：agent 与仓库都留在 WSL2，Windows 只承担编译与运行。**

```
┌────────────────── Windows 主机 ──────────────────┐
│  · .NET 10 SDK ✅ 10.0.401（见 §2）                      │
│  · Grim Dawn + IA 安装目录（游戏本体、图标资源来源）        │
│  · 浏览器（调试前端、打开程序界面）                       │
│  · C++ 工具链 —— 仅当要改 HookDll 时才需要               │
├────────────────── WSL2 · Ubuntu 24.04 ───────────┤
│  · ★ 仓库：/home/jyl/iagd      ← ext4 原生文件系统      │
│  · ★ agent（DSH）             ← bash/glob/grep 都在此执行 │
│  · VS Code Server + Remote-WSL                      │
│  · Node.js / npm / git / python3                    │
└──────────────────────────────────────────────────┘
```

### 1.1 为什么这样切分

按重要性排序，三条理由：

1. **agent 的工具链主路径是 Linux。** agent 的 bash / glob / grep / 沙箱机制是在 Linux 上训练出来的主路径；在 Windows 原生上改用 PowerShell 属于长尾能力，模型容易犯 Linux 肌肉记忆的错（路径、引号、编码、行尾）。这个坑到 2026 年仍未消失——同期 Claude Code 仍有
   [#51788](https://github.com/anthropics/claude-code/issues/51788)（设了 `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` 仍默认调 bash 工具）、
   [#45831](https://github.com/anthropics/claude-code/issues/45831)（默认吐 bash/Unix 语法）这类问题。
2. **工作量最大的一侧不依赖 Windows。** 线 A（新前端）与线 C（界面迁移，**工作量最大**）都是纯 Web 工作。目标架构把后端变成 HTTP 服务后，前端开发完全不需要 Windows。
3. **跨边界只发生在"编译这一刻"。** 编译读的是几百个 `.cs` + DLL 引用，不是几万个小文件；而 `npm install` 那种几万个小文件的操作，全部留在 WSL 原生文件系统上，不过 9p 边界。

一句话：**让 agent 待在它的母语环境里，让 Windows 只做它独占的事（编译 Windows 目标、跑游戏、开浏览器）。**

### 1.3 仓库位置：留在 WSL，不搬

**决策：仓库保持 `/home/jyl/iagd`，不搬到 Windows 盘。**

理由：

- **agent 是日常主力**，仓库在哪它就在哪干活。放在 `/mnt/c` 会让每次 `grep`/`glob`/`git`/`npm` 都过跨文件系统边界——315 个 `.cs` 还扛得住，`node_modules` 的几万个小文件会明显拖慢，而 npm 正是前端主力工作流。
- **跨边界编译的代价更小。** `dotnet build` 读的是几百个 `.cs`，量级远小于 `node_modules`。把开销放在编译这一刻，比放在每次文件操作上划算。
- **改主意的成本很低。** 仓库在 git 里，本来就"每步改动都提交"，真想搬就是一次 `clone`。

**实测性能（2026-09-11）**：

| 场景 | 耗时 |
|---|---|
| 首次构建（含 NuGet restore） | **63 秒** |
| 增量构建 / 无变化检查 | **5.3 秒** |

> **什么时候该重新考虑**：5.3 秒的增量让这个取舍**目前完全成立**。
> 只有当线 B/C 变成高频迭代、且实测明显变慢时，才考虑"Windows 盘再 clone 一份、用 git 同步"。
> （详细构建结果见 §4.2）

## 3. 跨边界：从 WSL 使用 Windows 工具

### 3.1 UNC 路径的坑（实测）

WSL 里的 `/home/jyl/iagd`，在 Windows 看来是 UNC 路径：

```
\\wsl.localhost\Ubuntu-24.04\home\jyl\iagd
```

而 **`cmd.exe` 不支持 UNC 路径作为当前目录**。直接 `cd` 过去会**静默退回 `C:\Windows`**，
只打印一段警告（GBK 编码，在 WSL 里显示为乱码）：

```
CMD.EXE 不支持 UNC 路径作为当前目录，默认值设为 Windows 目录。
```

命令看起来执行了，实际在**错误的目录**里——这是最危险的一类坑。

**解法：用 `pushd`**（它会临时映射一个盘符，实测映射为 `Z:`）：

```bash
cd /mnt/c && cmd.exe /c 'pushd \\wsl.localhost\Ubuntu-24.04\home\jyl\iagd && <你的命令> && popd'
```

实测 `pushd` 之后 `cd` 输出 `Z:\home\jyl\iagd`，并能正确列出 `IAGrim-core.sln` ✅

> **开头的 `cd /mnt/c` 是必须的。** `cmd.exe` 的*初始*工作目录由 WSL 传入（UNC 形式），会在启动时先打印那段警告。先切到 Windows 可见的目录，输出就干净了。
> 另外 `cmd.exe` 已在 PATH 中（`/mnt/c/Windows/system32/cmd.exe`），不必写绝对路径。

### 3.2 编译命令

```bash
cd /mnt/c && cmd.exe /c 'pushd \\wsl.localhost\Ubuntu-24.04\home\jyl\iagd && dotnet build IAGrim-core.sln && popd'
```

**关于 C++ 项目**：`IAGrim-core.sln` 里**只有 7 个 C# 项目**
（`IAGrim` / `Parser` / `DataAccess` / `StatTranslator` / `Cloud` / `EvilsoftCommons` / `DllInjector`），
**不含任何 `.vcxproj`**。所以这条命令**不需要 MSVC**。
`HookDll` 与 `injectAllTheThings` 的 C++ 工程独立于该解决方案，只有要改注入 DLL 时才需要在 Windows 装 C++ 工具链。

## 4. 日常工作流程

### 4.1 纯前端开发（最常用）

全在 WSL 内完成，**完全不碰 Windows**：

```bash
cd ~/iagd/WebUI
npm install          # 首次
npm run dev          # → http://localhost:3000
npm run lint         # 代码检查
```

浏览器（Windows 侧）直接打开 `http://localhost:3000` —— **WSL2 自带 localhost 转发**。

现有前端在浏览器里跑时 `isEmbedded === false`，走 `src/mock/` 假数据分支，
**纯布局/样式工作完全够用**（界面上的"加载 mock 物品"按钮仅开发模式显示）。

> `npm run dev` 直接用系统的 Node v22；若要对齐 `.node-version` 指定的 v20：
> `export PATH="$HOME/.local/share/fnm:$PATH" && fnm use 20`。

### 4.2 后端编译

```bash
cd /mnt/c && cmd.exe /c 'pushd \\wsl.localhost\Ubuntu-24.04\home\jyl\iagd && dotnet build IAGrim-core.sln && popd'
```

加 `-c Release` 可出 Release；`--no-restore` 跳过还原、加快增量。

**实测结果（2026-09-11 首次跑通）**：

| 场景 | 耗时 | 结果 |
|---|---|---|
| 首次（含 NuGet restore） | **63 秒** | 180 警告、**0 错误** |
| 增量 / 无变化 | **5.3 秒** | 19 警告、0 错误 |

产物落在 `IAGrim/bin/Debug/net10.0-windows/win-x64/`（48 个文件，含 `IAGrim.exe`、`IAGrim.dll`）。

**两个结论**：

1. **不需要 Visual Studio** —— SDK 自带的 MSBuild 足够构建整个解决方案。
2. **跨 `\\wsl.localhost` 构建的性能可以接受** —— 增量 5 秒，§1.3 的取舍成立。

> 那 180 个警告全是既有的可空引用与过时 API 警告（`CS8604`、`CS8602`、`SYSLIB0014`、`CS0612`），
> 与本次环境搭建无关，属于代码原有状态。

### 4.3 把前端产物送进运行目录

`WebUI/build.cmd` 是 Windows 批处理，**在本方案下有两个问题**：

1. 第一行 `fnm use` —— 依赖 fnm（已在 WSL 装好，但 bash 中需手动 `export PATH`）；
2. 末尾有 `pause` —— **agent 调用会永久挂住**（这是硬性禁止项，见 §4.5）。

WSL 等价流程：

```bash
cd ~/iagd/WebUI
npm run build

RES=~/iagd/IAGrim/bin/Debug/net10.0-windows/win-x64/Resources
rm -rf "$RES/assets"        # 文件名带内容哈希，不清会越积越多
cp -r build/. "$RES/"
```

> **顺序很重要**：先 `dotnet build` 生成 `bin/`，再拷前端产物。
> `bin/` 不存在时无处可拷——这是全新 checkout 上第一次构建最容易踩的坑。

输出路径里的 `win-x64` 来自 `IAGrim.csproj` 的 `<RuntimeIdentifier>win-x64</RuntimeIdentifier>`。

### 4.4 完整构建（要出成品时）

1. **编译后端** → 生成 `bin/`（§4.2）
2. **构建前端并拷贝** → `npm run build` + `cp`（§4.3）
3. **要 Release** → 把 §4.3 路径里的 `Debug` 换成 `Release`，并 `dotnet build -c Release`
4. 产物在 `IAGrim/bin/{Debug,Release}/net10.0-windows/win-x64/`

### 4.5 agent 的工作方式 ★

- agent 在 **WSL** 里，所有 `bash` / `glob` / `grep` / 文件读写都在 WSL 原生侧执行，工具语义与性能都是最佳状态。
- **后端编译由 agent 自己经 interop 闭环**，使用者不需要切到 Windows 手动敲命令：agent 执行 §4.2，就能看到真实编译结果并据此修正代码。
- **文件沙箱**：`/home/jyl/iagd` 可写；仓库之外只读。这意味着 agent 不能改写 Windows 盘的任何东西——若将来需要，要显式放宽策略。
- **铁律：不要调用 `WebUI/build.cmd`**（`pause` 会挂住 agent 的 shell）。用 §4.3 的 WSL 流程代替。
- **不要让 agent 在 `/mnt/c` 下做批量文件操作**：跨文件系统慢，且 `node_modules` 量级会放大这个问题。

### 4.6 git

仓库在 WSL，git 操作全部在 WSL 侧。实测：

- **没有 `.gitattributes`**
- **没有设置 `core.autocrlf`**（local / global 均未设）

当前无碍，因为 Windows 侧不参与 git 操作。⚠️ 若将来 Windows 侧也要 `commit`/`checkout`，
**先加 `.gitattributes` 固定行尾**，否则可能引入 CRLF 污染。

## 8. 开发数据服务（用真实数据开发）

> 位置 [`tools/devapi/`](../tools/devapi/)　状态：✅ **可用**（2026-09-11 验证）

### 8.1 解决什么问题

前端在浏览器里开发时**拿不到真实数据**：现有前端靠 WebView2 的 hostObjects
（同步私有调用）取数，`isEmbedded === false` 时只能走 `src/mock/` 假数据。
而浏览器**无法直接读 SQLite**。所以必须有中间层。

**方案**：一个只读的 Node 服务直读 `userdata.db`，暴露 REST。
它同时是 [`03-目标架构.md`](./03-目标架构.md) §4.2 **REST 草案的可运行原型**——

### 8.7 沙盒写模式（仅用于验证转移）

devapi 默认**只读**，但 A6（转移物品）需要走通**真实写链路**。为此有一套沙盒机制：

```
原库（只读）      ← 日常开发的 devapi（42500），绝不动
   ↓ 复制
沙盒库（可写）    ← 第二个 devapi（42501），只用于验证写操作
```

**① 建沙盒**：

```bash
mkdir -p ~/iagd-sandbox
cp ~/iagd-db-backup/userdata-20260911.db ~/iagd-sandbox/userdata.db
chmod u+w ~/iagd-sandbox/userdata.db
```

**② 启动写服务**：

```bash
IAGD_DB=$HOME/iagd-sandbox/userdata.db IAGD_WRITABLE=1 PORT=42501 \
  node tools/devapi/server.mjs
```

**③ 前端指向它**：

```bash
cd WebUI-next && IAGD_API_TARGET=http://127.0.0.1:42501 npm run dev
```

**★ 安全闸**：当 `IAGD_WRITABLE=1` **且**库路径恰好是原库时，服务会**拒绝启动**。
这条是硬编码的，专门防止误操作真实数据。

**转移做了什么**：复刻 `ItemTransferController.TransferItems` + `PlayerItemDaoImpl.Update`——
`StackCount` 递减 → 归零的记入 `deletedplayeritem_v3`、清掉 `ReplicaItem`、删除 `PlayerItem`。

⚠️ **与真实程序的差异**：真实程序还会把物品**写进游戏共享仓库存档**
（`TransferStashService.Deposit`），那需要 GD 存档的二进制格式、加密与校验和，devapi 不做。
所以沙盒验证的是**数据库侧 + 前端交互**，不是完整的转移。

**实测（2026-09-11）**：经前端转移一件 → 沙盒 66→65、**原库保持 66**、原库文件 mtime 未变。

## 9. C# 端 HTTP 服务（线 B / B1）

> 代码 [`IAGrim/Http/WebServer.cs`](../IAGrim/Http/WebServer.cs)　状态 ✅ 已实现、编译通过（2026-09-11）

新前端除了连 `tools/devapi`（开发原型），还能连**程序自己**提供的 HTTP 服务——
这才是"真正用起来"的形态。

| 项 | 值 |
|---|---|
| 实现 | **Kestrel**（ASP.NET Core），经 `FrameworkReference Include="Microsoft.AspNetCore.App"` 引用 |
| 端口 | **固定 `3031`**（`WebServer.Port`）；被占用则启动失败并记日志 |
| 监听 | `127.0.0.1`（仅本机） |
| 静态文件 | `GlobalPaths.StorageFolder`——与 WebView2 虚拟主机映射的是**同一个目录** |
| 认证 | 暂未加（决策见 [`03-目标架构.md`](./03-目标架构.md) §9） |

### 9.1 依赖与体积（实测，2026-09-11）

用 `FrameworkReference` 属于**框架依赖发布（FDD）**：Kestrel 来自共享框架，
**不会被拷进应用输出目录**。

| 项 | 实测值 |
|---|---|
| `IAGrim` 输出目录 | **48 个文件 / 20 MB** |
| 其中 ASP.NET Core / Kestrel 程序集 | **0 个**（一个都没拷进来） |
| `Microsoft.AspNetCore.App` 共享框架 | 29 MB（**由机器提供**，不进应用） |
| 对照 `Microsoft.WindowsDesktop.App` | 95 MB（IA 本来就依赖它） |

**结论：应用体积与安装包体积都不受影响。** 这也是选 Kestrel 而非
自己写 `HttpListener` 时不心疼的原因——路由、中间件、静态文件都是白拿的。

⚠️ 唯一要留意的是**运行时**：`Microsoft.AspNetCore.App` 与 `WindowsDesktop.App`
是**两个不同的共享框架**，只装 Desktop Runtime 的机器上没有前者。

- 开发机上已有（随 .NET SDK 装的 10.0.12）。
- 若要分发：按现有处理 .NET Desktop Runtime 的同样方式，检测/引导安装即可。
  相比 95 MB 的 Desktop Runtime，这 29 MB 是**很小的一笔**。

### 9.2 设计取舍：与旧路径并存

HTTP 服务**不替换** WebView2，只是多开一条通路：

| 通路 | 谁在用 | 通信方式 |
|---|---|---|
| 旧（保留） | WebView2 内嵌页面 | 虚拟主机 + `hostObjects` + `ExecuteScriptAsync` |
| **新** | **系统浏览器** | HTTP `/api/*` + 静态文件 |

它在 `MainWindow` 里启动，**失败了只记一条 Warn**，不影响程序其余功能——
符合「任何一步出问题都能退回去」。

### 9.3 数据来自同一套逻辑

`/api/*` 走 `SearchController.QueryItems` / `QueryCollection`，复用与界面
**完全相同**的链路（DAO → 副本信息 → `ItemStatService` 属性翻译 → `JsonItem`）。
所以浏览器里看到的物品与 WebView2 里一致，属性翻译也是**真正那套**
（不是 `tools/devapi` 的"简单层"复刻，见 [`08-属性翻译.md`](./08-属性翻译.md)）。

### 9.4 ★ 验证必须在 Windows 侧发起请求

程序监听的是 **Windows 侧的 `127.0.0.1:3031`**。
WSL2 的 localhost 转发**只覆盖 Windows → WSL** 这一个方向
（所以我们能在 Windows 浏览器里打开 WSL 的 `:3080`）；
**反过来 WSL → Windows 访问不到 `127.0.0.1`**。

后果：在 WSL 里 `curl http://127.0.0.1:3031` **会失败**，但服务其实是好的——
实测时这一度让我误判为"服务没起来"。验证要用 PowerShell：

```powershell
Invoke-RestMethod http://127.0.0.1:3031/api/health
```

### 9.5 运行 Debug 还是 Release（★ 数据文件不同）

`GlobalPaths` 里有条件编译，两者用的**数据文件完全隔离**：

| | Debug | Release |
|---|---|---|
| 数据库 | **`userdata-test.db`**（空库，会重新解析游戏数据） | `userdata.db`（**你的真实数据**） |
| 设置 | `settings-debug.json` | `settings.json` |
| storage | 共用 | 共用 |

- **Debug**：安全（不碰真实数据），但**没有你的物品**，且首次要重新解析游戏数据（慢）。
- **Release**：直接读真实数据（66 件物品立刻可用），启动快；但它**能写**真实数据库。

> 验证 HTTP 通路请用 **Release**——Debug 的库里没有玩家物品，
> `/api/items` 会是空的，验证不了真实数据链路。

### 9.6 从 WSL 运行编译产物的坑

**Windows 不能从 UNC 路径（`\\wsl.localhost\...`）运行 .NET 可执行文件**——
它不报错，只是静默什么都不发生（PowerShell 里连提示都没有）。
实测时我在日志里看到"程序根本没启动"才定位到。

做法：把 `bin/<Config>/net10.0-windows/win-x64/` **复制到 Windows 本地**再运行，例如
`C:\Users\<你>\iagd-release\`。

另外还要**补几个不在编译输出里的运行时依赖**（它们在安装目录
`C:\Program Files\IAGD\`）：`ItemAssistantHook_x64.dll`、`ItemAssistantHook_x64-GD12.dll`、
`ItemAssistantHook_playtest_x64.dll`、`dumpbin.exe`、`link.exe`、`mspdb140.dll`、`dllver.txt`。
缺 Hook DLL 时程序会卡在每秒一次的重试循环里。
