# 05 · 实施计划

> 本文回答：**分几步走、每步做到什么算完、做过哪些决定。**
> 设计依据见 [`03-目标架构.md`](./03-目标架构.md)。

---

## 1. 总体策略：两条线并行

```
线 A：新前端（不需要后端、不需要 Windows，只需 Node.js）
  0 → 1 → 2 → 3 → 4 → 5 → 6

线 B：后端服务化（需要 Windows + .NET SDK）
  HTTP/WS 与旧路径并存 → 验证 → 删旧路径

线 C：界面迁移与收尾（依赖 A + B）
  WinForms 界面搬进网页 → 删掉外壳
```

**线 A 现在就能开始**（用假数据），线 B 需要 Windows 环境，两条线可以并行。

**原则**：小步快跑，每步都能跑、能看、能验证，每步都提交 git。

## 2. 线 A：新前端（增量步骤）

| 步 | 目标 | 验证什么 | 需要后端 | 状态 |

| **0** | 页面能显示物品（**已改为真实数据**，不再用假数据） | 工具链 + 通信层通了 | ✅ | ✅ |
| **1** | 显示一列真实物品（用真实 `IItem` 类型） | 渲染逻辑 | ✅ | 🔴 |

| **4** | 视图切换（分栏列表 / 简洁卡片） | **P0 核心目标** | ❌ | 🔴 |
| **5** | hover 详情面板 | **P0 核心目标** | ❌ | 🔴 |

### 每步的完成标准

- **步 0**：浏览器打开 `localhost:3000` 能看到一条物品信息（**真实数据**）。✅ 已完成
- **步 1**：能看到一列真实物品，数据形状与真实 `IItem` 一致。
- **步 2**：页面上显示的是**数据库里真实存在的物品**。
- **步 3**：输入关键词能过滤结果。
- **步 4**：能用选择框在两种以上视图间切换。
- **步 5**：hover 任意物品能看到完整属性，且能滚动。
- **步 6**：点击 Transfer 后，物品真的回到游戏共享箱。

## 3. 线 B：后端服务化

| 步 | 目标 | 说明 |
|---|---|---|
| B1 | 加 HTTP 服务（REST） | 监听 `127.0.0.1:<PORT>`，**与现有 WinForms 路径并存** |
| B2 | 加 WebSocket | 推送消息；此时两条通信路径同时可用 |
| B3 | 前端切到新通信层 | 前端不再用 `hostObjects` |
| B4 | 启动时打开系统浏览器 | `Process.Start(url)` |
| B5 | 删掉 WebView2 | 移除引用与相关代码 |
| B6 | 删掉 WinForms 界面 | 只留 `NotifyIcon` |

**关键**：B1、B2 与旧路径并存期间，程序照常可用。
**任何一步出问题都能退回去**——这是这个顺序的最大价值。

| 步 | 目标 | 难度 |
|---|---|---|

## 6. 决策记录

> 只记"决定了什么 + 为什么"。过程属于 git 提交信息。

| 日期 | 决策 | 理由 |
|---|---|---|
| 2026-09-11 | 后端功能逻辑不做修改，只改外壳与界面 | 降低风险，保证可回退 |
| 2026-09-11 | 本仓库定位为自用分支，不顾虑上游兼容 | 使用者本人 fork 自用，无协作约束 |
| 2026-09-11 | 技术路线选 **C：后端服务化 + 浏览器访问** | 浏览器 DevTools 让样式开发效率质变；不受 WinForms/WebView2 双重限制 |
| 2026-09-11 | 前端**重做**而非改造 | 技术路线变了，通信层与界面都要重写；改造反而更费事 |
| 2026-09-11 | 前端框架用 **React**（替代 Preact） | 教程与生态最丰富，初学者遇问题容易搜到答案 |
| 2026-09-11 | 通信选 **REST + WebSocket** | 请求-响应用 REST；后端主动推送用 WebSocket |
| 2026-09-11 | WebSocket **沿用现有消息枚举** | 只换传输层不改语义，C# 与前端的状态处理逻辑都能保留 |
| 2026-09-11 | 采用"视图切换"而非单一布局 | 不同场景需求不同：找装备适合列表，浏览适合卡片 |
| 2026-09-11 | 视图组件与数据逻辑分离 | 新增样式成本低 |
| 2026-09-11 | **排除**"仓库网格 / 自由摆放"样式 | 固定位置排列与**检索工具**的设计意图不符，且把整理负担推给用户 |
| 2026-09-11 | hover 详情：hover 看简版 + 点击固定看全版 | 现有 tooltip 装不下双绿 MI 的 20+ 条属性，且不可交互 |
| 2026-09-11 | 托盘图标保留 `NotifyIcon`，不换第三方库 | 最成熟稳定；"用 WinForms 一个控件"不等于"用 WinForms 做界面" |
| 2026-09-11 | grimtools **只借鉴设计与 CSS，代码不能直接抄** | 它是 jQuery + 服务端渲染，技术栈不同（见 `.docs/06-外部参考.md`） |
| 2026-09-11 | 不引入 CSS 框架，沿用 CSS 变量方案 | 现有变量体系设计得好，够用 |
| 2026-09-11 | 不要 Visual Studio，用 VS Code + C# Dev Kit | 命令行 `dotnet build` 足够；唯一缺的 WinForms 设计器恰好用不上 |
| 2026-09-11 | **运行方式：agent 留 WSL，仓库留 WSL，Windows 只当「构建靶机」** | agent 的工具链主路径在 Linux；工作量最大的界面迁移不依赖 Windows；跨边界只发生在编译，`npm install` 的数万小文件留在 WSL 原生文件系统 |

## 7. 风险与注意事项

| 风险 | 说明 | 应对 |
|---|---|---|
| **C2 过滤器面板迁移** | 工作量最大，且涉及职业/技能/数值区间等复杂逻辑 | 放最后做；也可考虑先保留旧界面并行一段时间 |
| **数据丢失** | 物品数据库是多年积累 | 任何涉及数据库的改动先备份；不改动数据库结构 |
| **物品转移的即时性** | 现在是同步调用，改 HTTP 后要变异步 | 前端需要处理"请求已发出但结果未返回"的中间状态 |
| **程序生命周期** | 关了浏览器程序是否继续运行 | 托盘常驻；网页提供退出入口或只用托盘 |
| **WebSocket 断线** | 长时间运行可能断开 | 前端实现自动重连 + 重连后重新同步 |
| **性能** | 列表可能上千件，hover 面板频繁创建销毁会卡 | 复用面板实例；必要时做虚拟滚动 |
| **旧代码清理** | 两套前端并存期间容易混淆 | 新结构稳定后一次性删干净，不要长期并存 |
