## 1. 总体策略：两条线并行

```
线 A：新前端（不需要后端、不需要 Windows，只需 Node.js）
  0 → 1 → 2 → 3 → 4 → 5 → 6

线 B：后端服务化（需要 Windows + .NET SDK）
  HTTP/WS 与旧路径并存 → 验证 → 删旧路径

线 C：界面迁移与收尾（依赖 A + B）
  WinForms 界面搬进网页 → 删掉外壳
```

**线 A 现在就能开始**（用假数据），线 B 需要 Windows 环境，两条线可以并行。

**原则**：小步快跑，每步都能跑、能看、能验证，每步都提交 git。

### 3.1 ★ B5/B6 的实质：解耦，不是删除（2026-09-12 起）

**`MainWindow` 同时干着两件不相干的事**，这是删不掉它的原因：

1. **界面宿主** —— WebView2、搜索框、标签页。**已经不需要了**
   （`storage/` 换了新前端，浏览器接管界面，主窗口启动几秒后就被 `Hide()`）。
2. **整个应用的服务装配点** —— `MainWindow_Load` 里创建了转移控制器、CSV 解析、
   replica parser、后台备份、注入器、各种定时器与事件订阅，还有 B2 的广播点。
   `MainWindow_FormClosing` 则是**退出清理**（顺序 Dispose 掉上面这一堆）。

所以 B5/B6 的内容是**把第 2 件搬到一个不依赖 UI 的宿主**，而不是删代码。

#### 不能真的"一个窗口都不留"

| 为什么还需要窗口 | 说明 |
|---|---|
| 注入器 | 要一个消息窗口收 `WM_COPYDATA`（`RegisterWindow("GDIAWindowClass", ...)`） |
| 托盘图标 | `NotifyIcon` 需要消息循环；`Application.Run` 也得有个宿主 |

所以目标形态是 **`ApplicationContext`**（不可见、不承载界面），暂称 **AppHost**：

```
Program.cs
  → 服务装配（本来就在 MainWindow 之前：ServiceProvider / ParsingService / 自动解析）
  → Application.Run(new AppHost(serviceProvider, parsingService))
        ├── NotifyIcon（托盘：打开 web UI / 退出）
        ├── WebServer（Kestrel，127.0.0.1:3031）
        ├── 注入器 + RegisterWindow 消息窗口
        ├── CSV 解析 / replica parser / 后台备份 / WebSocketSync
        ├── ItemTransferController
        └── 维护窗口（按需创建，不是主界面）
```

#### 已经确认的两点

- **`Program.cs:323` 的 `_mw.Visible = false` 是无效的**：`Application.Run(_mw)`
  会把它重新显示，真正隐藏要等 WebView2 初始化完成（**几秒**）后的
  `BeginInvoke(() => Hide())`。这就是"启动时旧界面一闪而过"的成因。
  AppHost 落地后它自然消失。
- **`SearchController` 解耦很干净**：`public IBrowserCallbacks? Browser` 是**可空**
  的，HTTP 用的 `QueryItems()` 不经过它。删掉 WebView2 只需要不再给它赋值；
  旧界面才走的 `Search(...)` 没人调用即可。
- `UpdatingPlayerItemsScreen` 的进度来自 `StatUpdateUIBackgroundWorker` 的
  `progress` 回调——**"更新项目统计"本来就有进度接口**，只是接在 WinForms
  进度条上。将来要推到网页不需要新造轮子。

**关键**：B1–B4 之间"与旧路径并存"的策略已经完成使命，并且**已经收尾**——
2026-09-12 起 `storage/` 换成了新前端，**浏览器接管界面**；
随后 B5/B6 把 WebView2 与 WinForms 界面**全部删除**。

> **当时的顺序（先并存、再切换）是有价值的**：切换前能先验证新通路，
> 出问题删掉调用即可退回。验证完之后删旧的这一步，施工记录与踩到的坑见
> [`10-界面解耦.md`](./10-界面解耦.md)。
>
> ⚠️ **但 B5/B6 不能现在做**：Settings / Mods 等功能目前**只在新前端里补了一部分**，
> 旧界面一删就没了入口。先把功能补齐（见线 C）再删。

| 2026-09-12 | 轮询降级**保留**，只在 WS 断开时启用（不是删掉） | 后端重启、浏览器断线时界面不能变成死数据；`live === false` 才轮询 |
| 2026-09-12 | **数据库 / Mods 页面不迁移**，永久留在 WinForms（使用者决定） | 它是低频维护工具（加载数据库在游戏更新时是自动的、配置只在 IA 找不到游戏时用一次、清除与更新统计是排障），不值得为它把 `ParsingService` 的解析流程解耦。**影响 B5/B6：不能"只留 NotifyIcon"，要保留这个窗口** |
| 2026-09-12 | 「清除数据库」**不搬到网页**（后端端点保留但无入口） | 使用者问「这个按钮是干什么的、不会把东西都删了吧」。查证：它只 DROP 并重建 `DatabaseItem_v2` / `DatabaseItemStat_v2` / `ItemTag` 三张**游戏数据**表，不碰 `PlayerItem`（物品不会丢），但会让界面变成"物品还在、没名字没属性"。而它做的事「加载数据库」第一步就做了（先 `Clean()` 再解析）——**没有它做不到的事，却能制造一个看起来像物品全没了的界面** |
| 2026-09-12 | **改主意：数据库 / Mods 页面还是搬到网页**，不留 WinForms 窗口 | 使用者问「在 web ui 里不能做到和这个窗口一样的事情吗」。复查后发现成本比原先估计的低得多：`ProgressTracker` **本来就与 UI 无关**，焊死的只是 `WinformsProgressBar` 那层 20 行适配器。搬完 WinForms 界面就真的一个不剩了 |
| 2026-09-12 | 「配置」在网页上改为**粘贴路径** + 后端校验 | 浏览器出于安全**不允许**网页打开原生文件夹选择器。硬要保留那个对话框的话，就得为它留一整个 WinForms 依赖 |
| 2026-09-12 | 计数式的 `EnterMaintenance` 必须配「状态真的变了」的判断 | 实测踩到：`OnStateChanged` 每次进度更新都触发，把计数推到几十，`ExitMaintenance` 永远减不回 0 → **界面永久 503**、看起来像物品全丢了。用 `_maintenanceActive` 记住上次的值，只在变化时进出 |
| 2026-09-12 | 加载数据库期间**冻结 web UI**（而不是任其查询一个被清空的库） | `buttonForceUpdate_Click` 第一件事就是 `Clean()` 清空游戏数据库，之后是几分钟的解析。这期间网页查询会拿到空数据/不完整数据。改为：WS 广播 `maintenance` 状态、HTTP 查询端点返回 503、前端显示遮罩 |
| 2026-09-12 | 详情**渲染游戏原样 tooltip**（`replicaStats`），不从 `DatabaseItemStat` 重拼 | 游戏已经把它生成的完整 tooltip 原样给了 IA（带颜色代码、套装、授予技能、转换行）。实测这批物品的 `headerStats` **全是空的**、`bodyStats` 最多 4 条，重拼既费劲又不可能对齐 |
| 2026-09-12 | 颜色代码的 **RGB 值自己定**（`--tt-*`） | 代码→属性类型的对应是汉化包给的（`tags_ui.txt`），但**具体色值没有公开来源**——硬编码在游戏的 `gameengine.dbr` 里（Crate 论坛确认）。目标是"看起来像"，不是逐像素一致；日后挖到真值只需换变量 |
| 2026-09-12 | 技能与职业名**统一颜色**、英文技能名**不显示**、"需要"**不用红色** | 游戏那三处行为都依赖"当前人物"（按职业灰掉非本职技能、红色表示属性不够），而库里的装备不属于任何人物。见 `12-装备显示与交互.md` §1.2 |
| 2026-09-12 | **自己维护词缀表**，物品名由前端组装 | 原来靠"游戏当前汉化包 + 重新加载数据库"。使用者要求固定下来：`model/affixes.json`（503 条，含四个 DLC 文件）。任一侧词缀查不到就**整体回退**到 C# 拼的名字，宁可两个都用游戏文本也不要缺一半 |
| 2026-09-12 | 名字用**类型文本**（"传奇双手锤"）而不是品质枚举名（Epic/Blue） | 枚举名是数据库内部值，对使用者没意义；游戏原版的类型文本既说清品质也说清部位，而且它就在 tooltip 的 `type=66` 行里，不用自己拼 |
| 2026-09-12 | 布局改成**固定高度 flex 列**，只有物品列表滚动 | 使用者的原话是"滑动的时候只在这个框内滑动，表头不动"。⚠️ flex 列里 `.app` 与 `.app__content` 都必须 `min-height: 0`，否则内部滚动整个失效 |
| 2026-09-12 | 详情固定栏用 **grid 的列**而不是 `position: fixed` | 这样它天然位于工具条下方（"不顶头"），且栏宽由**模式**决定、**与是否选中无关**（"始终留空"） |
| 2026-09-12 | 前端**自带一份产物 + 启动时同步**到 storage | 原版 IA（`C:\Program Files\IAGD`）与我们共用用户数据目录，它启动时会用旧前端覆盖 `storage/`。自愈不能阻止覆盖，但能保证我们的程序一起来就修好。⚠️ 只碰前端文件，绝不动物品图标 |
| 2026-09-12 | **属性数值过滤不另写**，只补"可选项接口" | `PlayerItemDaoImpl` 里 `Filters`（属性存在性）与 `StatValueFilters`（数值，走 `ComputedItemStat` 预计算表）**早就实现**，旧界面一直在用；新前端缺的只是可选项与 UI。重写必然与旧界面行为不一致（违反「功能行为不能坏」） |
| 2026-09-12 | **过滤器定义搬到后端**（`Services/Filters/FilterCatalog.cs`），照搬旧面板 4 组 | 前端不再抄一份"勾了什么对应哪些 stat 字段"的映射。两份映射迟早漂移，而"勾了火焰抗性却按别的字段过滤"这种错几乎不可能被发现 |
| 2026-09-12 | 槽位清单**写死在 `SlotTranslator`**，不查数据库 | 实测 `DatabaseItemStat_v2` 里 `stat='Class'` 有 **175** 个值，混着容器、可破坏物、怪物、药水等非装备类别；旧界面（`UIHelper.SlotFilter`）用的也是这份固定清单 |
| 2026-09-12 | `filters/options` 的属性下拉**只列已预计算**的属性 | `statValueFilters` 直接查 `ComputedItemStat`；把没算过的属性列出来，使用者会选到一个永远查不到东西的条件 |
| 2026-09-12 | 搜索框的关键词**同时匹配属性名**（与名字是 OR） | 使用者 2026-09-11 的要求：「搜火焰抗性要找出带该属性的物品」。解析用两个来源——固定组的人工标签（伤害类属性没有同名模板，只能靠它）+ 语言表的同名模板 |
| 2026-09-12 | 关键词→属性的模板来源**排除 `customtag_*` / `iatag_*` / `tag*`** | 那些是组合模板（如 `{1} {3} 伤害`），key 不是数据库里的 stat 名，去掉占位符只剩"伤害"两个字，会把使用者引到一堆不存在的字段上 |
| 2026-09-12 | Minimal API **打开字符串枚举**（`ConfigureHttpJsonOptions`） | System.Text.Json 默认只认数字枚举，`"operator":"GreaterOrEqual"` 会返回 **400 且响应体为空**（实测很难查）；让前端传 `0..4` 太易错。只影响请求绑定，响应仍是 Newtonsoft |

## 7. 风险与注意事项

| 风险 | 说明 | 应对 |
|---|---|---|
| **C2 过滤器面板迁移** | 工作量最大，且涉及职业/技能/数值区间等复杂逻辑 | ✅ **后端风险已消除**（2026-09-12 实测通过）；剩下的纯前端可按既定信息架构（`09-高级搜索.md` §3–§4）分块做 |
| **数据丢失** | 物品数据库是多年积累 | 任何涉及数据库的改动先备份；不改动数据库结构 |
| **物品转移的即时性** | 曾是"改 HTTP 后要变异步"的顾虑 | ✅ **已结论：保持同步**。转移是写 CSV 交给游戏 hook，请求内就能返回成功/失败；实测双向都通，前端不需要中间状态。**仍需要一个刷新才看到列表变化**（B2 未做前靠轮询兜底） |
| **程序生命周期** | 关了浏览器程序是否继续运行 | 托盘常驻；网页提供退出入口或只用托盘 |
| **WebSocket 断线** | 长时间运行可能断开 | 前端实现自动重连 + 重连后重新同步 |
| **性能** | 列表可能上千件，hover 面板频繁创建销毁会卡 | 复用面板实例；必要时做虚拟滚动 |
| **旧代码清理** | 两套前端并存期间容易混淆 | 新结构稳定后一次性删干净，不要长期并存 |
