## 2. ★ 最有价值的发现：它的命名与我们的数据同源

抽样比对（29 个槽位 key + 22 个属性字段）：

| grimtools 的写法 | 含义 | 与我们的一致性 |
|---|---|---|
| `key="ArmorProtective_Head"` | 槽位（checklist 的值） | ✅ 与数据库 `Class` stat 的 textvalue **完全一致** |
| `raw/characterLife` | 人物属性 | ✅ `raw/` 之后就是**游戏 stat 名**，与 `DatabaseItemStat_v2.Stat` 同名 |
| `rawPB/characterLife` | **战宠加成**作用域下的同一属性 | 对应 C# `ItemSearchRequest.PetBonuses` |
| `base-defensiveProtection` | 该物品的**基础值**（不含加成） | `base-` 前缀 |
| `mastery/sk1211` | 专精加成 | 游戏专精记录 |
| `skill/sk1220` | 技能加成 | 游戏技能记录 |
| `modifier/sk1220` | 技能修正 | |
| `conversion/` + 两个伤害类型 | 伤害转化 | |

**实测命中率**：

- 槽位：**26 / 29** 与数据库 `Class` 值一致
- `raw/` 属性：**20 / 22** 在 `zh.txt` 里有同名模板

> **两处例外值得记**：
> - `ItemPrefix` / `ItemSuffix` / `ItemSet` **不是槽位**，而是"物品类别"，
>   对应 C# `ItemSearchRequest.Filters`（`List<string[]>`）那一类。
> - `skillManaCostReduction` / `offensivePhysicalMin` 在数据库里**确实存在**，
>   只是模板 key 带了前缀（`customtag_xpac_modif_skillManaCostReduction`）——
>   说明「stat 名 → 模板」存在**变体**，简单层会漏掉这类，详见 [`08-属性翻译.md`](./08-属性翻译.md) §5。

**结论**：我们可以**直接复用这套过滤器定义**，不必另创一套命名——
因为两边都是从同一份游戏数据里长出来的。

## 3. 信息架构（七个分区）

| 分区 | 内容 |
|---|---|
| **通用** | 名称（text）；类型（checklist，30+ 项：护甲 6 / 武器 14 / 饰品 4 / 其他 8）；稀有度（checklist：普通·魔法·稀有·史诗·传奇） |
| **武器属性** | 每秒攻击次数、穿刺比例、武器伤害（伤害类型下拉 + min/max） |
| **护甲/盾牌属性** | 基础护甲、伤害格挡、格挡概率、格挡恢复 |
| **物品属性** | 专精加成、技能加成、技能修正、人物属性、需求减少、进攻、防御、反击、转化、其他 |
| **战宠加成** | 与"物品属性"**同构**，但值前缀是 `rawPB/` |
| **需求** | 物品等级、玩家等级 |
| **杂项** | 套装物品、专属掉落、有设计图、能刷、能买、势力装备、扩展包（vanilla / gdx1 / gdx2 / gdx3） |

> ★ **这张表是 grimtools 的分区，不是我们的实现范围。** 我们 2026-09-12 落地的是
> **物品属性那一大块**，按旧 WinForms 面板切成 4 组：伤害 / 持续伤害 / 抗性 / 杂项
> （见 §6.2）。grimtools 的"武器属性""护甲属性""需求""杂项（套装/掉落/扩展包）"
> **暂未实现**——它们对应 C# 里已有的 `filters`（`setName` 等）与 `minimumLevel`，
> 将来要加是补数据、不是补能力。

## 4. 五种控件类型

| `type` | 用途 | 例子 |
|---|---|---|
| `text` | 名称 | `field="name"` |
| `checklist` | 多选 | 槽位（`key="ArmorProtective_Head"`）、稀有度、扩展包 |
| `checkbox` | 单选开关 | `field="isSetItem"` |
| `range` | min / max 数值 | `field="itemLevel"` |
| `select` | 属性名下拉（值即 `raw/xxx`）+ range | `field=""` |

> ★ **"添加..."按钮**：`select + range` 的组合块可以**重复添加多条**，
> 例如「火焰伤害 ≥ 30」AND「攻击速度 ≥ 10」。
> 这正对应 C# 的 `List<StatValueFilter> StatValueFilters`——
> 也印证了 §4.5 把搜索条件设计成请求体的选择是对的（query string 表达不了这种嵌套）。

### 6.1 ★ 属性名搜索（2026-09-12 实现）

搜「火焰抗性」会找出**带该属性的物品**，而不只是名字里含这几个字的。

实现：关键词 → 一组 stat 名 → 物品只要带其中任意一个就返回（与名字匹配是 **OR** 关系）。

解析来源两个，缺一不可：

| 来源 | 例子 | 为什么需要 |
|---|---|---|
| **固定组的人工标签** | 「抗性」+「火焰」→ `defensiveFire` 那组字段 | 游戏**没有**"火焰伤害"这样的模板（伤害是用带参数的组合模板渲染的），只靠模板匹配不出攻击类属性 |
| **语言表的同名模板** | `defensiveFire` = `{0}% 火焰抗性` | 覆盖固定组之外的属性，如"暴击伤害"→`offensiveCritDamageModifier` |

- 分词（空格）后**每个词都要命中同一段文本**，命中条目贡献的 stat 名取并集。
- 顺序两种都拼（"抗性 火焰"与"火焰 抗性"），所以"火焰抗性""火焰 抗性"都能命中。
- ⚠️ 模板来源**排除 `customtag_*` / `iatag_*` / `tag*`**：它们是组合模板
  （如 `{1} {3} 伤害`），key 不是数据库里的 stat 名，去掉占位符只剩"伤害"两个字，
  会把搜"伤害"的人引到一堆不存在的字段上。
- 实测：「火焰抗性」返回 **7 件**，逐件核对 `replicaStats` 都确实含该属性；
  搜「徽记」（普通名字搜索）返回 6 件，行为与从前一致。

### 6.2 `GET /api/filters/options`（2026-09-12 实现）

一次给全：品质 / 槽位 / 职业 / 数值比较符 / **分组复选框** / **属性下拉**。
完整形状与字段含义见 [`03-目标架构.md`](./03-目标架构.md) §4.5.2。

★ 关键设计：**"勾了什么对应哪些 stat 字段"由后端说了算**
（`IAGrim/Services/Filters/FilterCatalog.cs`，照搬旧 WinForms 面板
`IAGrim/UI/Filters/{Damage,DamageOverTime,Resistances,Misc}.cs` 的 4 组）。
前端不再抄一份映射——两份映射迟早漂移，而"勾了火焰抗性却按别的字段过滤"这种错很难发现。

两处**不是**照搬、而是修正的选择：

| 项 | 结论 | 原因 |
|---|---|---|
| 槽位清单 | **写死在 `SlotTranslator`**，不查库 | `DatabaseItemStat_v2` 里 `stat='Class'` 实测 **175** 个值，混着容器、怪物、药水等非装备类别 |
| 职业清单 | 滤掉没有名字的占位项 | 游戏数据里 55 条有 24 条是 `class0107` / `?` 这种，列出来只会干扰选择 |
| 属性下拉（`stats`） | 只列**已被预计算**的属性 | `statValueFilters` 直接查 `ComputedItemStat`，没算过的属性选了一定查不到东西 |

## 7. 前端实现（2026-09-12）

界面拆成**两块**，加起来正好覆盖 `ItemSearchRequest` 的全部过滤能力，互不重复：

| 组件 | 形式 | 管什么 |
|---|---|---|
| `FilterPanel` | 列表上方**可折叠**的一栏 | **勾选类**：品质 / 槽位 / 职业 / 四个属性分组（伤害 / 持续伤害 / 抗性 / 杂项） |
| `AdvancedSearch` | 搜索框旁的图标按钮 → **弹出**配置 | **输入类**：等级区间、属性数值条件（可加多条）、排序 |

### 7.1 外观

- 选项不是复选框，而是**圆角矩形色块**：未选中**阳刻**（顶边高光 + 底边投影），
  选中**阴刻**（整块压进去 + 换成强调色）。
- **一键清除**是**直角矩形**，故意与圆角选项区分；它只清过滤条件，**不动搜索框里的关键词**。
- 折叠头常驻一行，带"已选 N 项"角标——收起状态下也必须看得见有过滤在生效，
  否则会出现"为什么只剩 3 件"的困惑。列表为空时面板**依然渲染**，否则条件一严就再也清不掉了。
- 高级搜索图标是**自绘的内联 SVG**（三条带滑块的横杆）。grimtools 被 Cloudflare 挡着取不到图，
  而项目不引图标库 → [`14-疑难决定.md`](./14-疑难决定.md) §1。

### 7.2 状态与翻译

- 全部条件集中在 `views/useFilters.ts`：勾选状态、数值条件、等级、排序都存 `localStorage`
  （与 `usePaging` / `useItemView` 同一套路）。
- `buildSearchRequest()` 负责"界面勾选 → `ItemSearchRequest`"。**翻译集中在一处**，
  才能保证"勾了什么"与"发了什么请求"始终对得上：
  - `kind: 'stat'` 的选项 → `filters`（存在性；组内命**任意一个**字段即可，组间是 AND）
  - `kind: 'flag'` 的选项 → 对应的布尔字段（`socketedOnly` / `duplicatesOnly` / `petBonuses` …）
  - 高级搜索的每条数值条件 → `statValueFilters` 的一项
- ⚠️ **品质按值去重**：后端为兼容旧界面把 `Green` 返回三次（用 `prefixRarity` 区分），
  但多选与单值的 `prefixRarity` 不兼容，面板只保留 4 个品质值 →
  [`14-疑难决定.md`](./14-疑难决定.md) §2。
- 只有"关键词与过滤条件**全空**"时才走更轻的 `/api/items`，否则一律 `POST /api/search`。
