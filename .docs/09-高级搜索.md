## 2. ★ 最有价值的发现：它的命名与我们的数据同源

抽样比对（29 个槽位 key + 22 个属性字段）：

| grimtools 的写法 | 含义 | 与我们的一致性 |
|---|---|---|
| `key="ArmorProtective_Head"` | 槽位（checklist 的值） | ✅ 与数据库 `Class` stat 的 textvalue **完全一致** |
| `raw/characterLife` | 人物属性 | ✅ `raw/` 之后就是**游戏 stat 名**，与 `DatabaseItemStat_v2.Stat` 同名 |
| `rawPB/characterLife` | **战宠加成**作用域下的同一属性 | 对应 C# `ItemSearchRequest.PetBonuses` |
| `base-defensiveProtection` | 该物品的**基础值**（不含加成） | `base-` 前缀 |
| `mastery/sk1211` | 专精加成 | 游戏专精记录 |
| `skill/sk1220` | 技能加成 | 游戏技能记录 |
| `modifier/sk1220` | 技能修正 | |
| `conversion/` + 两个伤害类型 | 伤害转化 | |

**实测命中率**：

- 槽位：**26 / 29** 与数据库 `Class` 值一致
- `raw/` 属性：**20 / 22** 在 `zh.txt` 里有同名模板

> **两处例外值得记**：
> - `ItemPrefix` / `ItemSuffix` / `ItemSet` **不是槽位**，而是"物品类别"，
>   对应 C# `ItemSearchRequest.Filters`（`List<string[]>`）那一类。
> - `skillManaCostReduction` / `offensivePhysicalMin` 在数据库里**确实存在**，
>   只是模板 key 带了前缀（`customtag_xpac_modif_skillManaCostReduction`）——
>   说明「stat 名 → 模板」存在**变体**，简单层会漏掉这类，详见 [`08-属性翻译.md`](./08-属性翻译.md) §5。

**结论**：我们可以**直接复用这套过滤器定义**，不必另创一套命名——
因为两边都是从同一份游戏数据里长出来的。

## 3. 信息架构（七个分区）

| 分区 | 内容 |
|---|---|
| **通用** | 名称（text）；类型（checklist，30+ 项：护甲 6 / 武器 14 / 饰品 4 / 其他 8）；稀有度（checklist：普通·魔法·稀有·史诗·传奇） |
| **武器属性** | 每秒攻击次数、穿刺比例、武器伤害（伤害类型下拉 + min/max） |
| **护甲/盾牌属性** | 基础护甲、伤害格挡、格挡概率、格挡恢复 |
| **物品属性** | 专精加成、技能加成、技能修正、人物属性、需求减少、进攻、防御、反击、转化、其他 |
| **战宠加成** | 与"物品属性"**同构**，但值前缀是 `rawPB/` |
| **需求** | 物品等级、玩家等级 |
| **杂项** | 套装物品、专属掉落、有设计图、能刷、能买、势力装备、扩展包（vanilla / gdx1 / gdx2 / gdx3） |

> ★ **这张表是 grimtools 的分区，不是我们的实现范围。** 我们 2026-09-12 落地的是
> **物品属性那一大块**，按旧 WinForms 面板切成 4 组：伤害 / 持续伤害 / 抗性 / 杂项
> （见 §6.2）。grimtools 的"武器属性""护甲属性""需求""杂项（套装/掉落/扩展包）"
> **暂未实现**——它们对应 C# 里已有的 `filters`（`setName` 等）与 `minimumLevel`，
> 将来要加是补数据、不是补能力。

## 4. 五种控件类型

| `type` | 用途 | 例子 |
|---|---|---|
| `text` | 名称 | `field="name"` |
| `checklist` | 多选 | 槽位（`key="ArmorProtective_Head"`）、稀有度、扩展包 |
| `checkbox` | 单选开关 | `field="isSetItem"` |
| `range` | min / max 数值 | `field="itemLevel"` |
| `select` | 属性名下拉（值即 `raw/xxx`）+ range | `field=""` |

> ★ **"添加..."按钮**：`select + range` 的组合块可以**重复添加多条**，
> 例如「火焰伤害 ≥ 30」AND「攻击速度 ≥ 10」。
> 这正对应 C# 的 `List<StatValueFilter> StatValueFilters`——
> 也印证了 §4.5 把搜索条件设计成请求体的选择是对的（query string 表达不了这种嵌套）。

### 6.1 ★ 属性名搜索（2026-09-12 实现）

搜「火焰抗性」会找出**带该属性的物品**，而不只是名字里含这几个字的。

实现：关键词 → 一组 stat 名 → 物品只要带其中任意一个就返回（与名字匹配是 **OR** 关系）。

解析来源两个，缺一不可：

| 来源 | 例子 | 为什么需要 |
|---|---|---|
| **固定组的人工标签** | 「抗性」+「火焰」→ `defensiveFire` 那组字段 | 游戏**没有**"火焰伤害"这样的模板（伤害是用带参数的组合模板渲染的），只靠模板匹配不出攻击类属性 |
| **语言表的同名模板** | `defensiveFire` = `{0}% 火焰抗性` | 覆盖固定组之外的属性，如"暴击伤害"→`offensiveCritDamageModifier` |

- 分词（空格）后**每个词都要命中同一段文本**，命中条目贡献的 stat 名取并集。
- 顺序两种都拼（"抗性 火焰"与"火焰 抗性"），所以"火焰抗性""火焰 抗性"都能命中。
- ⚠️ 模板来源**排除 `customtag_*` / `iatag_*` / `tag*`**：它们是组合模板
  （如 `{1} {3} 伤害`），key 不是数据库里的 stat 名，去掉占位符只剩"伤害"两个字，
  会把搜"伤害"的人引到一堆不存在的字段上。
- 实测：「火焰抗性」返回 **7 件**，逐件核对 `replicaStats` 都确实含该属性；
  搜「徽记」（普通名字搜索）返回 6 件，行为与从前一致。


> ★ **2026-09-14 补丁：英文词要求词边界。** 关键词解析原先对索引文本一律做**子串**匹配，
> 于是搜 `LS` 会命中 `all ski**ls**` 之类的英文，解析出一堆无关属性——
> 使用者报的"搜 LS 出来了很多无关的选项"就是这个。
> 现在 `FilterCatalog.ContainsTerm()`：**中文照旧子串**（中文没有词边界，那也是主用法），
> **纯 ASCII 的词卡词边界**。
>
> 同一次还修了另一头：tooltip 里**界面上不显示**的英文技能名
> （`^s(Chillsurge)`，以及无码行里的裸括号 `(Chillsurge)`）原先留在
> `ReplicaItemRow.TextLowercase` 里参与子串匹配。现在两种形态都在
> `ReplicaTextFormatter.Searchable()` 里剔除，并加了迁移
> `RefreshSearchableReplicaText` 回填旧数据。
> 实测：搜 `LS` 的结果从 **23** 降到 **7**，而"火焰抗性""技能等级"这类属性名搜索不受影响。

### 6.2 `GET /api/filters/options`（2026-09-12 实现）

一次给全：品质 / 槽位 / 职业 / 数值比较符 / **分组复选框** / **属性下拉**。
完整形状与字段含义见 [`03-目标架构.md`](./03-目标架构.md) §4.5.2。

★ 关键设计：**"勾了什么对应哪些 stat 字段"由后端说了算**
（`IAGrim/Services/Filters/FilterCatalog.cs`，照搬旧 WinForms 面板
`IAGrim/UI/Filters/{Damage,DamageOverTime,Resistances,Misc}.cs` 的 4 组）。
前端不再抄一份映射——两份映射迟早漂移，而"勾了火焰抗性却按别的字段过滤"这种错很难发现。

两处**不是**照搬、而是修正的选择：

| 项 | 结论 | 原因 |
|---|---|---|
| 槽位清单 | **写死在 `SlotTranslator`**，不查库 | `DatabaseItemStat_v2` 里 `stat='Class'` 实测 **175** 个值，混着容器、怪物、药水等非装备类别 |
| 职业清单 | 滤掉没有名字的占位项 | 游戏数据里 55 条有 24 条是 `class0107` / `?` 这种，列出来只会干扰选择 |
| 属性下拉（`stats`） | 只列**已被预计算**的属性 | `statValueFilters` 直接查 `ComputedItemStat`，没算过的属性选了一定查不到东西 |

## 7. 前端实现（2026-09-13）

界面拆成**两块**：

| 组件 | 形式 | 管什么 |
|---|---|---|
| `FilterPanel` | 列表上方**可折叠**的一栏 | 快速勾选：品质 / 槽位（护甲·武器·首饰·物品）/ 职业 / 四个属性分组 / **入库时间**（单独放最后一行，单选；**不选就是不限**，选中显黄）。**实时生效** |
| `AdvancedSearch` | 搜索框右边的图标按钮 → **居中模态**（快捷键 s） | **搜索条件**（不是过滤器！见下）：**顶部自带搜索框** + 类型 / 稀有度 / 职业 / 物品属性 / 等级区间 / 属性数值。**草稿态**，点「完成」才生效 |
| `FilterDialog` | **只在专注模式**下按 f 弹出 | 过滤选项 + **视图工具条**（专注模式把工具条藏起来了）。实时生效 |

> 为什么高级搜索与过滤面板内容重复（见 [`14-疑难决定.md`](./14-疑难决定.md) §13）：模态是"想在一个地方
> 把条件看全"的去处。

★ **2026-09-13 改版（使用者要求，见 [`14-疑难决定.md`](./14-疑难决定.md) §14、§18）**：

1. **排序搬去工具条**（`views/useSort.ts`）：升级成"入库时间 / 品质 / 等级 / 名称"四级，
   默认入库时间。高级搜索里**不再有**排序。
2. ★ **它是"搜索条件"，不是"过滤器"**：勾"穿刺伤害" = 搜「某某装备 AND 穿刺伤害」，
   只决定搜出来什么，**不改动过滤器的配置**。所以状态是**两套**
   （`useSearchConditions` / `useFilters`），请求里合并（两类之间 AND）——
   详见 [`12-装备显示与交互.md`](./12-装备显示与交互.md) §4.8。
3. 模态**顶部加了搜索框**（关键词也走草稿），这才是一个完整搜索栏该有的样子。
4. 模态内是**草稿**：点「完成」写回**搜索条件**；「取消」/×/Esc = 丢弃。
5. 「完成」旁边有「取消」；主界面另有「**退出搜索**」——关键词 + 搜索条件一起清掉，
   **不动过滤器**。
6. 快捷键：`/` 搜索框、`f` 过滤面板、`s` 开关高级搜索、`c` 清过滤器；
   模态内 Enter = 完成、`c` = 重置搜索条件、Esc = 取消。

### 7.1 颜色即逻辑

| 外观 | 含义 |
|---|---|
| 圆角矩形、未选中 | **阳刻**（顶边高光 + 底边投影；底色比面板**亮**一档——凸起的东西是受光的） |
| **黄**、阴刻（凹陷） | **与**：同时满足 |
| **绿**、阴刻 | **或**：满足任意一个 |
| 直角矩形「清除 / 重置全部」 | 一次性动作，故意与"可反复切换的选项"长得不一样；只清过滤条件，**不动**搜索框关键词 |

- **逻辑挂在组上**：点**组名**（四个属性分组、以及**职业**）在"与 ↔ 或"之间切换，
  组名显示黄/绿；组里的选项只有选中/未选两态，**颜色跟随组**。
- 品质 / 槽位没有切换（天生是"或"，选中即绿）；开关类没有切换（独立布尔，选中即黄）；
  **槽位那四组**的组名是快捷**全选 / 全不选**，与逻辑无关。
- ⚠️ 职业的"或"需要一个后端字段（`classesAny`）：原来每个职业各一条子查询，天然只有"与"。
- **入库时间**那几个档位互斥（不是"或"），但按使用者要求也用**黄**表示选中；不选即"不限"。
- 折叠头在「清除」后面有一行图例。落地细节见 [`14-疑难决定.md`](./14-疑难决定.md) §8。
- 分区名（护甲 / 武器 / 首饰 / 物品、四个属性组）**可点 = 全选 / 全不选**。
- 折叠头常驻"已选 N 项"角标（**宽度固定成两位数字并始终占位**，否则勾第一项时会把它右边的
  「清除」和图例顶开，整页跟着跳）；**列表为空时面板依然渲染**——否则条件一严就再也清不掉了。
- 高级搜索图标是**自绘的内联 SVG**（三条带滑杆的横杆）：grimtools 被 Cloudflare 挡着取不到图，
  项目也不引图标库 → [`14-疑难决定.md`](./14-疑难决定.md) §1。

### 7.2 状态与翻译

- 全部条件集中在 `views/useFilters.ts`，存 `localStorage`（与 `useItemView` / `usePaging` 同一套路）。
- ★ 该文件分两层：`useFilterState(initial)` 是**纯状态 + 操作**（不落盘），`useFilters()` 是
  主状态（额外持久化）。高级搜索的草稿就是前者的第二个实例——两处共用同一份操作实现，
  才不会出现"草稿里勾出来的东西"和"主状态里勾出来的"语义不一致。
- `buildSearchRequest()` 负责"界面勾选 → `ItemSearchRequest`"。**翻译集中在一处**，
  才能保证"勾了什么"与"发了什么请求"始终对得上：
  - 属性项按**所在组的逻辑**分组：组是"与"时各选项各占一组、组是"或"时该组所有选项合并成**同一组**
    —— 后端 `filters` 是"组间与、组内或"，正好对应
  - 职业的"或"走 `classesAny`（后端的职业过滤只有"与"一种，合并成 `IN` 才是"或"）
  - `flag` 项 → 对应的布尔字段（`socketedOnly` / `enchantedOnly` / `hasPetBonus` …）
  - 品质 → `rarityConditions`，key 是"值:词缀数"（`Green:2` = 双稀有）
  - 槽位 → `slot`；**所有物品** → 全部装备槽位 + `slotInverse`
  - 高级搜索：数值条件 → `statValueFilters`；入库时间 → `recentHours`；等级 → `minimumLevel` / `maximumLevel`
  - **排序** → `sortBy`（`created` / `quality` / `level` / `name`），SQL 由后端 `BuildOrderBy` 拼；
    它**不是过滤条件**，不参与 `IsEmpty`、也不计进"已选 N 项"
- ★ 2026-09-13 起**不再走 `/api/items` 那条"更轻"的路**：排序必须在后端 SQL 里做
  （分页切片在后端），而 `GET /api/items` 不接受排序参数。两个端点背后本来就是同一个 DAO
  调用（空请求 ≈ 无条件搜索），所以统一 `POST /api/search` 并不更重。
