# 10 · 界面解耦（B5/B6 的施工图）

> 本文回答：**怎么把 `MainWindow` 去掉，而不丢掉功能。**
> 背景与动机见 [`05-实施计划.md`](./05-实施计划.md) §3.1；进度见 [`00-当前状态.md`](./00-当前状态.md)。

**建立于**：2026-09-12（依据一次对 `MainWindow.cs` 的全量只读审计）

---

## 1. 为什么不能直接删

`MainWindow` 同时干着两件不相干的事：

1. **界面宿主** —— WebView2、搜索框、设置页、标签页。**已经不需要**
   （`storage/` 换了新前端，浏览器接管界面）。
2. **整个应用的服务装配点与消息循环宿主** —— `MainWindow_Load`（610–887 行，约 66 项）
   + `MainWindow_FormClosing`（368–422 行，19 项 `Dispose`）。

所以 B5/B6 的实质是**搬家**。

### 一个反直觉的好消息

**引用 `MainWindow` 这个类型的，全仓库只有两处**：

| 位置 | 用途 |
|---|---|
| `Program.cs:24/39/302/318/331` | 构造、`Visible=false`、`Application.Run(_mw)`、静态属性 |
| `LanguagePackPicker.cs:124` | `Program.MainWindow?.UpdateLanguage()`（模态框关闭后刷新整窗语言） |

其余全是**注释里提到**（`ModsDatabaseConfig.cs:40`、`WebServer.cs:111/263`）。
`StartupService.cs` 完全不引用它。`IAGrim/Http/` 下只有 `WebServer.cs` 的注释提到，
没有代码级类型引用。

**这意味着删窗口不难，难的是搬装配。**

## 2. ★ 关键决策：隐藏的宿主 Form，而不是 `ApplicationContext`

曾考虑用 `ApplicationContext` 做宿主，但审计发现**三处硬要求 Form/Control**：

| 组件 | 要求 |
|---|---|
| `MinimizeToTrayHandler`(`MinimizeToTrayHandler.cs:18`) | 构造签名就是 `(Form, NotifyIcon, ...)`，还订阅 `Form.SizeChanged`、读写 `WindowState`/`Hide()` |
| `WindowSizeManager`(`MainWindow.cs:822`) | 要求 `Form`，订阅 `FormClosing` |
| `DarkMode`(`MainWindow.cs:745`) | 要求一个 `Control` 当 root |
| `CustomWndProc`(`MainWindow.cs:429-466`) | 用 `MainWindow.Invoke` 从注入线程切回 UI 线程 |

**结论：保留一个不可见的宿主 Form**，`Application.Run(host)` 照旧。
这样上面四样**一行都不用改**，`ApplicationContext` 方案省下的复杂度远小于它带来的改造量。

宿主只需要：`Visible = false`（并用 `SetVisibleCore` 阻止被显示）、一个 `NotifyIcon`、
一个 `Invoke` 能力。**不需要任何 Designer 控件。**

#### 实测（完整跑了两遍"加载数据库"）

```
t=8s   LoadingTags 0%      step 1/11
t=32s  LoadingItems 0%     step 3/11
t=49s  SavingItems 41%     step 6/11
t=81s  完成 → maintenance=False，items=64（玩家的物品全程完好）
```

#### ⚠️ 实测抓到的严重 bug

**维护模式计数泄漏**：`MaintenanceService.OnStateChanged` 在**每次进度更新**时
都触发（一秒好几次），而 `EnterMaintenance` 是**计数**式的。于是跑完一次
「加载数据库」深度涨到几十，`ExitMaintenance` 永远减不回 0，
**界面永久卡在 503**——用户的物品看起来"全没了"。

修法：用 `_maintenanceActive` 记住上次广播的 Busy，只在**真的变化**时进出。
教训：**计数式的 enter/exit 必须配一个"状态真的变了"的判断**，
否则任何高频事件都会把它推爆。

## 7. 坑（审计中发现的，踩之前先看）

1. **HTTP 服务的生命周期挂在 WebView2 回调里** —— 这是 P1 必须先做的原因。
2. **`Program.cs:318` 的 `_mw.Visible = false` 是无效的**：`Application.Run(_mw)`
   会重新显示它，真正隐藏要等 WebView2 初始化完成（**几秒**）后的 `BeginInvoke(Hide())`。
   这就是"启动时旧界面一闪而过"的成因。
3. **每个 B2 广播点都耦合了 WinForms 对象**，没有一个是纯后端事件。
4. **`CustomWndProc` 里的 `_searchWindow.ModSelectionHandler`** 是注入链路唯一的真界面依赖。
5. **退出清理漏了 `_webServer.Dispose()`**。
6. **启动时的自动解析发生在 `MainWindow` 创建之前**（`Program.cs:268-287`），
   那时 `WebServer` 还不存在 → 解析期间网页**连不上**（而不是看到维护遮罩）。
   宿主提前后应该顺带修好：让 HTTP 服务在自动解析之前就起来。
7. `DarkMode` 以 `MainWindow` 自身当 root（`DarkMode.cs:30`），删窗口时注意它的 `Dispose`。
8. `MainWindow.NumInstantSyncItemCount`(`MainWindow.cs:79`) 是**死字段**，仓库内无引用。

### 实际踩到的（2026-09-12）

9. **`WinForms` 的 `Load` 事件只在窗体首次显示时触发**。`SetVisibleCore(false)`
   让窗口永不显示 → `Load` 永不触发 → 整个应用起不来（HTTP 服务、注入器、
   CSV 解析全都不启动，日志停在 `Running the main application..`）。
   装配改为构造函数末尾显式调用，注入器从 `Shown` 改为直接启动。
10. **不要用 `Form.TopLevel` 判断"这个窗口是否被嵌进 Panel"**。
    `Form.TopLevel` **默认就是 `true`**，只有 `UIHelper.AddAndShow` 会把它设成
    `false`。删掉 `AddAndShow` 之后，`if (!config.TopLevel) { ...设置边框... }`
    就**永远不进入**，`ModsDatabaseConfig` 的 `FormBorderStyle = None`
    （Designer 里为嵌入而设的）原样保留 → 独立显示时**没有标题栏、没有关闭按钮**。
    正确做法：装配时无条件设好窗口属性。
