## 1. ★ 详情直接用**游戏原样导出的 tooltip**

这是本页最重要的一个决定。

| 数据源 | 内容 | 用不用 |
|---|---|---|
| `JsonItem.replicaStats` | **游戏原样导出的完整 tooltip**：带 `^X` 颜色代码、套装、授予技能、伤害转换行、需求行，顺序与游戏内一致 | ★ **用它** |
| `JsonItem.headerStats` / `bodyStats` | IA 自己从 `DatabaseItemStat_v2` 翻译拼出来的 | 仅在 `replicaStats` 为空时兜底 |

**为什么**：

- 游戏通过 `ItemReplica` 把它生成的 tooltip **原样**给了 IA，IA 存进库。
  全部 64 件实测物品都有，最多的一件 **81 行**。
- 从 `DatabaseItemStat` 重新拼一套不可能对齐——实测这批物品的
  `headerStats` **全是空的**，`bodyStats` 最多 4 条（而且只有技能加成那种）。
  转换行、套装层级、授予技能这些更是拼不出来。

代价是它**只能是文本行**（不是结构化数据），但"接近游戏效果"这个目标
本来就要求逐行还原，结构化反而是障碍。

### 1.1 `^X` 颜色代码

游戏在 tooltip 文本里嵌 `^` + 一个字母的颜色标记（`^-` 表示恢复默认）。
代码 → 属性类型的对应写在游戏的汉化包里（`tags_ui.txt` 开头那张
"物理伤害—棕色——{^E}"的表）。

⚠️ **具体 RGB 没有公开来源**——它硬编码在游戏的 `records/game/gameengine.dbr`
里（Crate 论坛的 "Text Color Codes?" 一帖确认了这点）。
所以 `global.css` 里那套 `--tt-*` 是**按颜色名 + 游戏观感定的**，
目标是"看起来像"，不是逐像素一致。

### 1.2 按使用者要求做的三处偏离

游戏原版有几个行为在"物品库"这个场景下没意义，已改掉（实现在
`ReplicaStatList.tsx` + `ReplicaStatList.css`）：

| 游戏里 | 库里 | 为什么 |
|---|---|---|
| 技能名带英文（`黑死病 (Black Death)`） | **只显示中文** | 使用者不要英文。游戏把英文包在 `^s` 里 → CSS `display:none`；另一种旧格式（`type=81`）没有 `^s`，按"含技能等级的行"删括号 |
| 非本职业技能灰掉 | **按职业分色** | 游戏按**人物职业**算，但库里的装备不属于任何人物。所以不跟人物走，改成每个职业一个固定色（取自各职业主图） |
| "需要 玩家等级/灵巧"是红色 | **普通色** | 那是和人物属性联动的提示，库里没有"当前人物" |

> ⚠️ 删英文括号时**不能无差别删**：普通属性里的 `(OA)` `(DA)` `(AS)` `(CDR)`
> 是缩写，必须保留。所以只对"技能等级"行动手。

> ⚠️ 同一个代码在不同语境下语义不同：`^F` 在属性行是"活力伤害"（桃红），
> 在技能行是职业名（`^g<^F神秘^g>`）。所以"技能行统一颜色"必须**按行判断**，
> 不能只靠 CSS。

### 1.3 配色 / 缩进 / 职业名：对着游戏校准（2026-09-12）

- **颜色**：`--tt-*` 那批原先按"颜色名 + 观感"猜，现在换成**游戏内实测值**
  （使用者对着游戏给的）：词缀绿 `#10EA5D`、MI 基底绿与 `^L` 元素 `#91CB00`、
  虚化 `#00e1b8`、速度 `#bc93c5`。
  ⚠️ 大小写敏感：`^w`（基底名白）与 `^W`（武器数值）是两个不同的码。
- ★ **深色背景可读性**：这几档颜色改过几轮（使用者每次看效果后提的）：
  · **`^M` 流血**：`#7f0000`（栗，游戏原值）**对比度只有 1.54**，在深色面板上几乎
    看不见 → 2026-09-14 提亮成 `#e35a5a`（柔和的粉红）→ **2026-09-15 使用者要
    "更接近暗红 crimson"，改成 `#d02b45`**（色相 ≈350°，略带品红；在提亮后的
    面板上对比度约 2.7——要暗红就得接受这个取舍）；
  · **`^R` 火焰**：2026-09-14 要"正红"取了 `#ff3b30`；2026-09-15 又反馈
    "**燃烧伤害的亮度太刺眼**"，于是调成 **`#e0512f`**——还是红、略偏橙有火焰感，
    但亮度压下一档。它与流血 `#d02b45` 的**蓝通道差得远**（47 vs 69），
    一个偏橙、一个偏品红；
  · **混乱**单独造了一个码 **`^Q`**（深粉 `#e1336d`），原来它和 `^F` 活力同色。
  （对比度按**当时**的面板底色算；面板本身在 2026-09-15 从 `#1f1c18`/`#26231f`
  提亮到了 `#322c25`，所有深色属性文字的对比度都随之略降。）

### ★ 1.3.1 自定义码：配色表里的"码"是我们自己的（2026-09-14）

使用者定的一条原则：

> **"我们已经脱离了游戏里的那些颜色分类，而是我们在自己写表了，
> 所以我们可以自己任意地创造不同的颜色组。"**

所以**码不必沿用游戏的**。约定：

- **从游戏没用过的字母里挑**，免得和 tooltip 原文里的码撞车。
  汉化包里出现过的码是
  `E n H P C O b R T F Z B y Y r w G g s L S M N K W t o j C D`
  —— 所以 `Q`（以及 `A I J U V X`）是干净的。
- 目前只有一个自定义码：

  | 码 | 含义 | 色 | 落点 |
  |---|---|---|---|
  | `^Q` | **混乱**（伤害 / 反击 / 抗性 / 最大抗性） | `#e1336d` 深粉 | `global.css` 的 `--tt-chaos` + `ReplicaStatList.css` 的 `.tt-Q` |
  | `^O` | 体格 / 所有类型伤害 / 最大全抗性 | `#e08a3c` 橙 | `--tt-body` + `.tt-O` |

  演进过程：混乱原先跟 `^F` 活力**共用同一个颜色**（`#ff68b3`，界面上分不出来）→
  按汉化包的"混乱伤害—橙色"改过一次（使用者不认）→
  使用者从游戏里"混乱"的代表画面（深紫星空）取色，给了
  `#952a6a` / `#e1336d` / `#781e54` 三个候选，定下 `#e1336d`。
  ⚠️ 一开始我是**直接改 `--tt-chaos`**，那等于把 `^O` 的**所有**用途
  （体格、所有类型伤害、全抗性）一起染成深粉——使用者指出后拆成了两个码。
- **缩进**：三级（0 / 1 / 2），按行的 `type` 分档；个别要看**上下文**——
  `type 82` 里既有"技能名"也有"技能参数"，两者差一级，只能看它是否紧跟
  "授予技能抬头"（`type 81`）。
- **职业名**：按职业分色（`--cls-*`，10 个色取自各职业主图），尖括号跟着职业色；
  技能名与"所有技能"用 `--tt-value`。

### 1.3.2 两处字号强调（2026-09-14，使用者对着游戏截图提的）

| 行种 | 是什么 | 样式 |
|---|---|---|
| `type 21` | **套装名**（`达加隆的毁灭`） | 青色 `--tt-set-name` + **1.15em** + 加粗 |
| `type 29` / `type 43` | **镶嵌物 / 增幅这一大块的标题**（`虚化之魂`、`风暴之剪铭文`） | 金色 `--tt-header` + **1.15em** + 加粗 + **上方一条淡分隔线** |
| `type 31` | 那两块的**小标签**（`镶嵌物`、`史诗增幅`） | 灰色小字，**不动** |

- 套装名原先跟下面的成员名（`type 23`）一样大，分不出主次；
- 镶嵌物 / 增幅是游戏 tooltip 里的**独立小节**，起点要看得出来 →
  `border-top: 1px solid rgba(255,255,255,.09)`（用低透明度白；`--border` 在深底上偏黄、太实）。

> ⚠️ **行内的颜色码会盖住行种样式**：镶嵌物的名字是 `^sC30^o虚化之魂`，
> 那个 `^o` 会被解析成 `.tt-o`——原先它是给"套装说明的括号注记"用的**灰**，
> 于是标题色被压掉，看上去还是灰的（使用者："虚化之魂怎么还是灰色的呀"）。

### ★ 原则：冲突时**行种优先**（2026-09-14）

使用者追问"你现在还在看 `^X` 来给样式吗"，引出了这条原则。现状是**两套逻辑**：

| 类别 | 谁说了算 | 例子 |
|---|---|---|
| **属性色** | **我们的表**（`recolorStats` 覆盖） | `^O活力伤害` → `^F`；`+120% 酸性伤害` → `^G` |
| **行内语义标记** | 仍照游戏给的码 | `^s`(英文名) `^c`(技能名) `^o`(次要文本) `^w`(白) `^r`(需求) `^g^F`(职业标记) |

第二类之所以留着，是因为 **`^X` 是一行**之内**唯一的分段信息**——
`+300% ^G酸性伤害^- ^E持续 ^H5 ^E秒` 一行三种颜色，光靠"行种"切不出来。

**但同一个码在不同行种里含义不同**（`^o` 在套装说明里是"注记"、在镶嵌物名字里是"标题"），
这时**行种更懂这一行**，所以：

- ❌ 不要给码一个"默认色"（那会压过行种，逼着每个冲突点去打补丁——
  第一版就是这么干的：`.tt-type-29 .tt-o { color: inherit }`）；
- ✅ **默认中性（`inherit`），只在明确的行种里显式给色**：

  ```css
  .tt-o { color: inherit; }              /* 行内"次要文本"标记，不自带颜色 */
  .tt-type-22 .tt-o { color: var(--tt-flavour); }   /* 只有套装说明的注记是灰 */
  ```

> **教训：调"整行"的样式时，先看这行原文里有没有 `^X`** ——
> 内层 span 的选择器虽然短，但作用在更里层，`color` 直接生效。
>
> 想**彻底不看 `^X`** 就得自己算分段（用词表 + 规则把一行切开），
> 那是另一件工程；目前这套混合方案性价比最高。

> ⚠️ **第一次做反了**：我把 `type 31`（"镶嵌物"/"史诗增幅"两个词）放大了。
> 使用者说的"镶嵌物 / 附魔"是指**那一整块**，不是那几个字——要放大的标题是
> `type 29`（镶嵌物的名字，`虚化之魂`）与 `type 43`（增幅的名字，`风暴之剪铭文`）。
> 教训：**先确认行种到底代表什么数据**（这次是查库看 `type 29/31/43` 的实际文本），
> 再动样式，别按字面猜。

★ 两处都用 **`em`** 而不是 px：这样设置页里的"字号倍率"（固定栏详情 / 详细对照）
能连它们一起缩放。

### 1.4 套装区与套装授予技能（2026-09-13 使用者报的两个 bug）

以「复仇粉碎者」的真实 `replicaStats` 为例（`type` 是行种）：

```
[21] 自然复仇者                        ← 套装名（青）
[22] "莫格卓根祝福的铠甲…"              ← 套装说明（灰）
[23] 复仇者的铠甲 / 肩铠 / …            ← 成员（金）
[23] (2) 套装 / (3) 套装                ← 层级标题（金）
[28] +4% 攻击能力(OA)                   ← 套装加成
[28] <守誓>重击 (Smite) 技能等级 +3      ← 套装加成里的"技能等级"
[82] ^g<^F士兵^g>^c佐尔汉的技艺          ← 套装授予技能：名字
[83] 75% 的武器伤害                     ← 参数
[82] 自然复仇者(受到攻击时有 50%…)       ← 套装授予技能：名字
[82] 复仇者的精神在你体内膨胀。           ← 说明
[82] 12 ^E秒^E技能冷却时间               ← 参数
[82] ^w恢复 ^H12% ^w生命                ← 参数
```

**bug ①**：套装授予技能整块都是 `type 82`（普通授予技能是 `37` 名字 / `39` 说明 /
`81·82·83` 参数）。于是**名字和说明被当成"技能参数"渲染成了米黄**
（"自然复仇者"和"复仇者的精神在你体内膨胀。"都是黄的）。

→ 修法：`ReplicaStatList.tsx` 新增 `skillRowKind()`，按**文本形状**在 `type 82` 里
区分三者（以句号结尾 → 说明；带 `(…施放该技能)` 或 `<职业>` → 名字；其余 → 参数），
挂上 `.tt-skill-name` / `.tt-skill-desc` 两个类，回到与普通授予技能同一套色。
顺带修了缩进：套装区的参数行原先也是 1 级（没有 `type 81` 抬头可依），现在按形状兜底成 2 级。

**bug ②**：套装加成（`type 28`）那些行在游戏导出时**本来就没有 `^X`**，
旁边却夹着"技能等级 +3"这种会被前端**补色**的行（`colorizePlainSkillRow`），
于是整块"部分白、部分花"。

★ **2026-09-13 用三件装备核对过：`type 28` 是"整类无码"**：
德里格的战衣里同一个属性——套装技能区写 `+300% ^G酸性伤害^-`（带码），
套装加成区写 `+120% 酸性伤害`（**一个 `^` 都没有**）；复仇粉碎者、伊斯坎德拉
两件也是同样的规律。**根因是汉化包作者没给那些条目加色**（他给 `Damage*` 系列
加了，套装加成用的模板没加），不是游戏官方没配。

→ **修法（2026-09-13，最终版）**：新增 `model/statColors.ts`——一张
**以工程自带的汉化包为唯一标准**的「属性关键词 → 颜色码」表（见 §6.2），
渲染前用它**重新着色整行**。套装加成因此被补上，而普通属性行上"某份包给错了"
的颜色也一并纠正：

`+120% 酸性伤害` 绿、`+110 攻击能力(OA)` 棕、`+25% 施法速度(CS)` 紫、
`50% 的 混乱伤害 转换为 酸性伤害` 橙+绿。

> ⚠️ 中间有两版过渡：先是"`type 28` 整块保持默认色"（使用者当时说"如果全都是
> 白色的那还好"），后是"用统计出来的表补无码的行"。使用者 2026-09-13 定了最终
> 立场——**以我们自带的表为准，全部覆盖**——前两版都被这一版取代。

> **`^w` 不再特殊**：`^w恢复 ^H12% ^w生命` 里的"生命"以前被 `^w`（普通白）罩着，
> 现在照样按本表覆盖成 `^F`（桃红）——重新着色对"有没有码"一视同仁。

★ **"前端一共在哪些地方按字符串上色"的完整清单**（含这张表的来历与抽取方式）见 §6。

## 2. 物品名的颜色
### 2.1 基础名：按**底材**（颜色问游戏）

基底名的颜色**照游戏的名字行来**（`replicaStats` 的 `type` 3-7）：按 `nameCore`
的位置往前找**最近的那个 `^X`**。三档：

| 名字行长什么样 | 基底名用什么色 | 例子 |
|---|---|---|
| 带 `^l`（**稀有底材**） | 游戏给的**黄绿** | `^g幽灵束缚(…)· ^l萨拉查的王者之剑 ^g·崩碎现实(…)` |
| 带 `^w`（普通底材） | 游戏给的**白** | `^g暴怒(…)· ^w保护者 马裤 ^y·野猪(体格/精神)` |
| **一个 `^X` 都没有** | **什么都不加，继承容器的品质色** | `崩碎世界之 恶魔的 血誓魔印`、`神话 哈鲁德的极寒之握` |

> ⚠️ **第三档才是绝大多数**：实测库里 89 行名字行，**66 行一个颜色码都没有**
> （游戏导出时按角色/版本省略了）。2026-09-14 之前这里给"取不到码"**兜底成 `^w`（白）**，
> 于是把品质色压掉了 —— 使用者报的「**血誓魔印**本身是稀有的（不是 MI），
> 怎么看不出稀有」就是这个。**兜底成"不加码"才对**：让它继承
> `qualityClass(item.quality)` 给的品质色（稀有绿 / 史诗蓝 / 传奇紫 / 魔法黄）。
>
> 教训：**"取不到信息"时不要塞一个具体值**，那会把本来正确的继承链打断；
> 让上层（这里是容器的品质色）说话。

### 2.2 词缀：**我们自己维护词缀表**

> ★ 这一节是 2026-09-12 改过的。原来靠"游戏当前汉化包 + 重新加载数据库"，
> 使用者要求改成**程序自带**一份，不依赖它。

`WebUI-next/src/model/affixes.json` 是**内置的词缀表**，从使用者提供的汉化包
**全目录**提取（503 条）：

| 来源文件 | 条数 |
|---|---|
| `tags_items.txt` | 385 |
| `aom/tagsgdx1_items.txt` | 54 |
| `foa/tagsgdx3_items.txt` | 47 |
| `fg/tagsgdx2_items.txt` | 10 |
| `tags_ui.txt` / `foa/tagsgdx3_ui.txt` | 7 |

其中 `^g`（稀有绿）344 条、`^y`（魔法黄）144 条、带推荐标记 `☆` 的 100 条。

**名字由前端组装**（`composeItemName`）：

```
^g恒定☆·   +   保护者 胸铠   +   ^y·雄鹰☆
  前缀绿         基础名（稀有度色）    后缀黄
```

数据来自 C# 新加的三个字段：

| 字段 | 内容 | 来源 |
|---|---|---|
| `prefixTag` / `suffixTag` | 词缀的 tag 名（如 `tagPrefixB001_Sh_A`） | `Tags` 里按 record 查 `lootRandomizerName` |
| `nameCore` | **纯基础名**（如 "保护者 马裤"） | 见下面的坑 |

⚠️ 任一例词缀查不到时**整体回退**到 C# 拼好的 `item.name`——宁可两个词缀都用
游戏文本，也不要显示成缺一半的半成品。

⚠️ **这个表是静态数据**：游戏加了新词缀就要重新提取一次。

#### 踩到的两个坑

1. **提取的正则写窄了**。DLC 的 tag 形如 `tagGDX1PrefixB104_WpnMelee1h_A`
   ——`Prefix` 前面还有 DLC 代号，所以 `tag(?:Prefix|Suffix)` **一条都匹配不到**，
   整整漏了 118 条，导致几件装备只能回退。正确的是
   `tag\w*(?:Prefix|Suffix)\w*`。
2. **基础名不只是 `itemNameTag`**。游戏的名字是
   `prefix + quality + style + name + suffix`（汉化包第一行的
   `{%_s0}…{%_s4}` 模板）。"保护者 马裤"里 **"保护者"来自 `itemQualityTag`**，
   只拼 `itemNameTag` 会得到光秃秃的"马裤"。改用与 `GetItemName` 相同的模板、
   只是不带前后缀。

> ⚠️ `^y` / `^g` 的样式**按容器限定作用域**：同一个 `^g` 在 tooltip 的职业标记
> （`^g<^F神秘^g>`）里是尖括号的颜色，不能共用一条规则。

## 3. 三种视图

注册在 `WebUI-next/src/views/registry.ts`，**加一行就多一种**（视图只接
`items` + 回调，不碰数据逻辑）：

| id | 名称 | 用途 | 「详情」可选方式 |
|---|---|---|---|
| `table` | 分栏列表 | 表格式，关键信息分栏对齐，精确找装备 | 左 / 右固定栏（**没有浮动**） |
| `compact` | 简洁卡片 | 图标 + 名称 + 关键标签，快速浏览 | 浮动 / 左 / 右固定栏 |
| `compare` | 详细对照 | **完整属性并排摊开**，筛选后比较几件装备 | **全部显示 / 固定高度**（管卡片怎么排，见 §3.2） |

★ **详情方式按视图区分**（使用者 2026-09-14，写在 `ItemViewDefinition.detailModes`）：

- **分栏列表**是逐行扫视的表格，浮动面板跟在鼠标旁边会一直挡住相邻的行，
  所以只留左右固定栏；
- **简洁卡片**是网格、卡片大小不一，浮动预览正合适，三种都保留；
- **详细对照**不挂侧栏面板（`showsFullStats`），它的下拉管的是**卡片布局**。

★ **每个视图各存一份偏好**（同一个 localStorage 键里按视图 id 存 map）：
分栏列表选"右固定栏"、简洁卡片选"浮动"、详细对照选"固定高度"，三者互不干扰。
旧的版本只有一个全局字符串，读到时当作所有视图的默认值（键 `'*'`）。

### 3.2 详细对照的两种卡片布局（2026-09-14，使用者要求）

| 模式 | 卡片高度 | 排列 |
|---|---|---|
| **全部显示**（默认） | 随内容 | **瀑布流**：每张卡接在同一列上一张的结尾 +12px，各列顶部**错落**，高卡片旁边不留大片空白 |
| **固定高度** | **上限** = 内容区高度 × **0.8**；一行都装得下时按该行最高的卡 | flex 换行、**行内等高** |

- 瀑布流用 **CSS 多列**（`column-width: 330px` + `break-inside: avoid`）——不需要
  JS 量高度，也不会把一张卡拆到两列里。⚠️ 多列的填充次序是**纵向**的
  （先填满第一列再第二列），不是从左到右逐行。
- 固定高度的 0.8 倍由 `CompareView` 测量 `.app__content`（列表 / 固定栏所在的那
  一行）的 `clientHeight` 写进 `--compare-fixed-height`；用 `ResizeObserver`
  跟着走，所以**窗口缩放、过滤器面板开合、专注模式切换**都会同步改。
- ★ 固定高度是**上限**，不是"每张都硬撑到 0.8"（使用者 2026-09-15 补充）：
  一行里每张卡的内容都装得下时，**行高压到该行最高那张卡**，不在下面留一大片空白。
  实现只有两条 CSS：flex 容器的**默认 `stretch`**（行内等高）+ 卡片的 `max-height`
  ——于是 `行高 = min(该行最高卡片的内容高度, 上限)`，**不需要 JS 分行或量高**。
- 超过上限的卡片在**卡片内部滚动**（`TooltipCard` 的属性区本来就可滚，
  还带上下两条遮罩条）；内容少的卡片被 `stretch` 拉到行高，下面**留空白**。

`compare` 视图的"同一行以最宽的为准"**不用 JS 量高度**：flex 换行时行高天然取
该行最高的项（也因此免疫"图标加载完高度才变"的时序问题）。但每张卡自己的**边框
只包自己的条目**，所以容器用的是 `align-items: flex-start` 而不是 `stretch`——
使用者 2026-09-12 给过参考图并明确过这一点（早先按 stretch 做过，矮卡下面会空一片）。

### 3.1 布局：只有列表滚动

使用者 2026-09-12 要求"滚动只发生在物品列表那个框里，表头不动"，所以整页
不再是长滚动文档，而是**固定高度的 flex 列**：

```
┌─────────────────────────────────┐
│ header / tabs        flex: none │ ← 不滚
│ 搜索 + 视图工具条     flex: none │ ← 不滚
├───────┬─────────────────┬───────┤
│ 左栏  │ 物品列表         │ 右栏  │ ← 只有列表自己 overflow-y
│(可选) │ (独立滚动)       │(可选) │
└───────┴─────────────────┴───────┘
```

布局层是单独的 `AppShell.tsx`（它要用详情面板的 Context，而 `App` 自己在
Provider 外面取不到）。

⚠️ flex 列里 `.app` 与 `.app__content` 都必须 `min-height: 0`，否则子元素
撑高后 flex 不收缩，**内部滚动会整个失效**（这是 flex 布局的经典陷阱）。

★ **列宽、居中与窄屏**（使用者 2026-09-14 定，实现在 `global.css` 与
`TableView.css`）：

- **分栏列表的表格自己有宽度上限并居中**（`max-width: 54em` + `margin: 0 auto`）：
  名称列最宽 **25 个汉字**；**类型列按"最长的类型文本"预留宽度**——库里目前
  实测最长是"史诗双手远程武器"（8 字），使用者要求按"**双稀有双手远程武器**"
  （10 字）留够，所以给 10 个汉字内容 + 内边距（`width: 12em`）。
  超长用省略号截断（`table-layout: fixed` 锁列宽）。窄到 `min-width: 25em`
  以下时表格不再压缩，改由列表容器出**横向滚动条**。
- 单元格左右内边距压到 **8px**（使用者："把里面的内容稍微往左右两边拉一下"）——
  表格总宽基本不变，省下的横向空间都给了文字。
- 类型 / 等级两列**居中**，**表头也要**（"类型"两个字居中）。⚠️ 选择器必须写成
  `.item-table th.item-table__center`：上面那条 `.item-table thead th{text-align:left}`
  的特异性是 (0,1,2)，裸的单类选择器只有 (0,1,0)——压不住它，表头就会留在左边
  （使用者 2026-09-14 报的正是这个）。
- 表格顶端**贴住**列表容器上沿（`:has(> .item-table)` 去掉那 10px 顶部内边距）。
- ★ **滚动容器拆成「外壳 + 滚动层」两层，遮罩条钉在外壳上**（使用者 2026-09-14）：

  | 外壳（不滚动） | 滚动层 |
  |---|---|
  | `.app__list` | `.app__list-scroll` |
  | `.tt-card__body` | `.tt-card__body-scroll` |

  外壳 `position: relative; overflow: hidden`，只负责边框、裁切，以及上下两条
  **6px 高、与容器背景同色**的 `::before` / `::after`（`position: absolute`）。
  滚动条一出现，文字就在离边框 **6px** 处被"遮住"而不是硬切；滚到底时它只是
  一段留白（不会盖住最后一行）。**内边距解决不了**这个问题——内边距属于滚动
  内容，内容照样从边框滚过去。

  ⚠️ **不能**把遮罩条做成滚动层自己的 `sticky` 伪元素：sticky 元素的粘性约束
  矩形是**父元素的 content box**，越不过父元素的 `padding`——容器有 10px 内边距
  时，条子最多停在离边框 10px 处（使用者第一次看到的就是"没贴在最底下和最顶上"）。

  ⚠️ 遮罩色必须等于**背后的容器**颜色：列表是 `--bg-sunken`；详情面板底色是
  `--bg-panel`（由 `.item-detail` 设 `--tt-mask-bg`），弄错就会露馅。
- ★ **背景分三层，卡片才"浮"得出来**（使用者 2026-09-15）：

  | 层 | 变量 | 值 | 用在哪 |
  |---|---|---|---|
  | 页面底 | `--bg` | `#1c1a17` | `body` / `#root` |
  | 列表 / 卡片区的底 | `--bg-sunken` | `#131109` | `.app__list`（含它的遮罩条、表格吸顶表头） |
  | 卡片与面板 | `--bg-panel` | `#322c25` | `.item-card` / `.compare-card` / `.item-detail` / 各种弹窗与工具条控件 |

  原来 `--bg-panel` 一个色既当卡片、又当卡片所在的容器，于是详细对照的卡片、
  简洁卡片的卡片都"糊"在列表里分不出来（详情面板 `#1f1c18` 也和页面几乎同色）。
  ⚠️ 动这三层时有两处必须**跟着走**，否则遮罩条会露馅、表头会透出滚动内容：
  列表的 `::before/::after` 遮罩条与 `.item-table thead th` 用 `--bg-sunken`；
  `.item-detail` 的 `--tt-mask-bg` 用 `--bg-panel`。
  ℹ️ 面板提亮后深色 tooltip 文字的对比度会略降；如果觉得某几档"发闷"，
  优先按 §1.3 里记的取舍逐个调（颜色本身也在随使用者的观感迭代）。
- **详情固定栏**始终 380px，是 grid 的一列（不是 `position: fixed`）。
- ★ **宽屏行为按视图分开**（使用者 2026-09-14 追加澄清："视图里每一种都是
  独立的样式调整"）：
  · **分栏列表**：页面足够宽（视口 ≥ 1624px）时三列对称——
    `[固定栏 380] [列表 ≤68em] [固定栏 380]`——整组轨道居中，于是表格中线与
    页面中线重合、固定栏贴页面边、另一侧**留空**。
  · **简洁卡片**：固定栏占一侧，**另一侧卡片铺满**（`auto minmax(0,1fr) auto`
    的填满布局），不居中、不留空。所以那条宽屏规则带 `data-view='table'`，
    只作用于分栏列表。
- 页面**不够宽**时两者一样：列表与固定栏占满宽度、列表不居中、另一侧不留空。
- **极窄（≤750px）**：固定栏与浮动详情都**不显示**，列表吃满整行。
  750 这个数 ≈ 固定栏 380 + 分栏列表最小宽度（≈25em），再窄两边会互相挤压。

## 4. 交互

### 4.1 详情面板的显示方式（**按视图不同**）

工具条上的「详情」下拉框切换，偏好存 `localStorage`：

| 模式 | 行为 | 哪些视图有 |
|---|---|---|
| `hover`（浮动） | 跟随鼠标浮动，鼠标移开即消失 | 简洁卡片 |
| `docked-left` / `docked-right` | 在左/右侧**固定一栏**。选中了显示选中的，没选中就跟着 hover 走 | 分栏列表 / 简洁卡片 |

★ **面板的内容 = `TooltipCard`，与「详细对照」的卡片是同一个组件**
（`components/ItemTooltip/`）。使用者 2026-09-14："item-detail 应该和
compare-card 的样式一样才对（字体、字号、颜色），他们的代码应该是复用的。"
两者本来就是同一种东西——把游戏原样导出的 tooltip 摊开给人看。现在图标 /
名字 / 等级 / 属性区都在这个组件里，使用方只剩外壳（一边是侧栏 / 浮动面板，
一边是网格卡片），各自不同的按钮经 `action` 插槽传入：面板放「取消固定」
（`item-detail__close`）、对照卡片放「取出」（`transfer-btn`）。
统一之后两处的字号（原来 11px vs 12px）与内边距再也不会各自漂移。

★ 分栏列表**没有浮动**的理由与收敛逻辑见 §3（表格逐行扫视，浮动面板会挡住
相邻行；偏好不被当前视图支持时由 `effectiveDetailMode` 回退，且不写回存储）。

★ 固定栏**不是 `position: fixed`**，而是 grid 的一列、面板是普通文档流元素。
这样它天然位于工具条下方（"不顶头"），且栏宽由**模式**决定、
**与是否选中无关**（"无论是否选中都留空"）。

⚠️ 有个真实冲突要处理：面板平时是 `pointer-events: none`（否则 hover 时它
会挡住指针、立刻触发 `mouseleave` 导致闪烁），但固定栏**必须能滚动**。
而且鼠标从卡片移向面板时会经过空白、离开卡片——按原逻辑内容会被清空，
刚想滚动就没了。所以固定栏模式下：**始终接收鼠标事件**，
且鼠标移开卡片时**保留内容**（移到别的卡片上仍会正常换）。

#### 浮动面板摆在哪（2026-09-14）

使用者给了两条定位要求，实现在 `ItemDetailPanel.tsx` 的 `floatingStyle()`：

1. **放在卡片的另一侧**：卡片在屏幕左半就放右边、在右半就放左边。那一侧放不下
   时自动翻到另一侧，仍放不下就贴住视口边。点击选定的那张也走同一套，
   所以"选中后浮在另一侧"与"悬浮时跟随"表现一致。
2. **垂直与卡片中线对齐**：面板通常比卡片高，所以拿面板**自身高度**去算居中——
   高度由组件在浏览器绘制前用 `useLayoutEffect` 量出来（因此不会闪）。
   面板比视口还高时以"能完整看到"为先，夹在上下边距之间。

⚠️ 面板的挂载不能和"该不该显示"混在一个条件里：`hover` 模式下必须**仍然挂载**
（`{floatingPanel && <ItemDetailPanel />}`，放在 `.app__dock` 之外），
否则 hover 什么都不会出现（2026-09-13 踩过一次）。

#### 页脚整块删掉（2026-09-14）

使用者要求删掉浮动模式下的 `item-detail__foot`。这一行原来装三样东西，都在
库里没有意义：

| 原来有什么 | 为什么删 |
|---|---|
| `baseRecord`（`^g暴怒(物血/OA/酸血抗)·…`） | 游戏内部记录名，用户看不懂 |
| 「转移到游戏」按钮 | 卡片和列表本身就有「取出」；按钮离卡片又远，反而绕 |
| 「硬核」标签 | 账号维度的属性，逐件物品显示没有信息量 |

于是面板只剩「抬头 + 属性区」两块，浮动与固定栏两种形态完全一致。
（固定栏模式 2026-09-13 就已经没有这一行。）

> **使用者问：来源是从哪儿获得的数据？有哪些类型？**
> 字段是 `item.type`，由 C# 的 `ItemTypeDto` 填（`Utilities/ItemHtmlWriter.cs`）：
> `Recipe`=图纸、`Buddy`=好友共享、`Player`=自己的物品、`Augmentation`=镶嵌物、
> `Unknown`=兜底。浏览器列表里**实际只会出现 `Player`**（好友 / 图纸不走这条通路），
> 所以卡片上那一栏永远是同一个值——2026-09-14 删掉。
>
> **使用者问：硬核影响什么东西？**
> `isHardcore` 决定物品属于**普通角色还是硬核角色**（筛选分组、转移目标、按角色区分），
> 是**账号/角色维度**的属性；列表本来就按当前角色过滤过了，逐件显示没有信息量——
> 同一天从「简洁卡片」和详情页脚里一起删掉。

#### 抬头与图标（2026-09-14）

- 详情抬头里的 `item-type`（"传奇护肩"）**删掉**：tooltip 属性区第一行本来就是
  `tt-type-66 tt-indent-0`，两者完全重复。抬头只留等级。
- ★ 图标规则统一成**一条**（使用者 2026-09-14 逐条定）：**外框一律 64×64，
  只有首饰缩到原尺寸 32×32**。

  | 位置 | 外框 | 图片 |
  |---|---|---|
  | 简洁卡片 `.item-card__icon` | 64×64（带底色圆角） | 顶格 |
  | 详情面板（固定栏 / 浮动）`.item-detail__icon` | 64×64 | 顶格 |
  | 详细对照 `.compare-card__icon` | 64×64（带底色圆角） | 顶格 |
  | **以上三处的首饰**（勋章 / 项链 / 戒指） | 不变 | **32×32**，居中 |

  "顶格" = `object-fit: contain` 缩放到外框内（宽图占满宽、高图占满高），
  既不留出多余缩放、也不拉伸。首饰图标实测只有 **32×32**
  （`storage/*.tex.png` 里 1109 个），放大到 64 会糊——所以按原尺寸居中显示。

  ⚠️ 判据是**槽位**（`model/slot.ts` 的 `isJewelrySlot()`）。实测 `/api/items`
  返回的 `slot` 是**本地化文本**（"勋章"/"戒指"/"项链"），不是
  `SlotTranslator` 的原始键——C# 侧 `ItemHtmlWriter` 已经翻译过一道；
  函数两种写法都认，将来若改回原始键也不用动。

### 4.2 取消选中

- 点面板里的关闭
- 再点一次同一件
- ★ **点任意空白处**（`mousedown`，不是 `click`——拖滚动条/选文字不该触发；
  点在物品卡片上时不取消，那是"改选另一件"）

### 4.3 焦点框

hover 与选中用同一色系、**不同强度**（`--focus-accent` /
`--focus-hover-bg` / `--focus-pinned-bg`）。

用**左侧竖条**而不是只换背景：列表行本来就细，纯背景变化容易被忽略。

⚠️ 竖条画在**第一个单元格的 inset 阴影**上，**不是** `tr` 的 `border-left`
（使用者 2026-09-14 给的截图）：`border-collapse: collapse` 下 `tr` 的边框是
**表格层的共享边框**，`position: sticky` 的表头背景**盖不住它**——滚动时
表头行的高度范围内会漏出这条竖条，看起来就像"图标列从表头左侧漏出来"。
换成 inset 阴影后它属于普通内容，会被表头正常遮住；而且不占布局
（也就不需要再"预留 3px 防跳动"）。

### 4.4 「取出」按钮

两种视图里都有，**不必先选中弹详情**。方形、图形化、拟物化——实体感靠
CSS 做：竖向渐变模拟受光、内侧顶部高光 + 外侧投影让按钮浮起、按下时换成
内凹阴影并下沉 1px。

- 就地反馈：成功/失败直接换图标，两秒后复位（取回是"点一下就走"的操作，
  弹面板反而碍事；但失败必须让人看见）
- `stopPropagation`（连 `mousedown` 一起拦）：不能让点击冒泡到卡片，
  否则会顺带选中它

### 4.5 排序（工具条，2026-09-13）

工具条上「排序」下拉，四个选项，**默认入库时间**（偏好存 `localStorage`）：

| 选项 | 次序 |
|---|---|
| 入库时间 | 入库时间（新 → 旧） |
| 品质 | 品质（传奇在前）→ **等级降序** → 名称 |
| 等级 | **等级降序** → 品质 → 名称 |
| 名称 | 名称 → 品质 → 等级 |

> ⚠️ 品质排序里的等级**也是降序**（使用者 2026-09-14 报"选品质时等级还是从低到高，
> 反了"）。品质只是第一关键字，同一个品质内仍然"高等级在前"，与「等级」排序一致。

★ 排序**必须由后端做**（`PlayerItemDaoImpl.BuildOrderBy`）：分页是 `LIMIT/OFFSET` 切片，
前端自己重排只会让"第几页"对不上。每一条排序都以 `PI.Id` 收尾，保证全序、
翻页时不重不漏。

⚠️ 品质的值是数据库里的 `Epic` / `Blue` / `Green` / `Yellow`，而 IA 上游的命名是**交叉**的
（`Epic` = 传奇、`Blue` = 史诗，见 `ItemCard/quality.ts`），所以 SQL 里用
`CASE PI.Rarity WHEN …` 映射成权重，不能直接按字符串排。

设置 → **字体**：一项就够——**物品属性区**的字体族与字号倍率（0.5–2），

### 4.8 ★ 搜索条件与过滤器是**两回事**（2026-09-13 使用者澄清）

**心智模型**（使用者原话的意思）：

> 高级搜索里的选项**不是过滤器**。勾"穿刺伤害"就等于搜「某某装备 AND 穿刺伤害」，
> 它只决定**搜出来什么**；搜到的结果，你可以再拿过滤器去筛。
> 就像搜名字一样——搜名字出一批结果，然后对这批结果用过滤器。
> 点"完成"**不该**改动过滤器的配置。

所以前端有**两套独立的状态**，请求里合并成一个 `ItemSearchRequest`：

| | 存哪 | 谁在用 | 角标 |
|---|---|---|---|
| **搜索条件** | `useSearchConditions()`（`iagd.search.filters` / `iagd.search.advanced`） | 高级搜索弹窗（草稿态，点「完成」才写回） | 高级搜索按钮上的数字 |
| **过滤器** | `useFilters()`（`iagd.filters` / `iagd.advancedSearch`） | 过滤面板（实时生效） | 折叠头上的"已选 N 项" |

**合并规则**（`buildSearchRequest`）：两类条件之间是 **AND**。

- 属性存在性 / 数值条件 / 开关类：各自成条，后端本来就是"组间与"，直接叠加 ✓
- 等级区间：求交（`0` = 不限）；入库时间：取更严格的那档 ✓
- 品质 / 槽位 / 职业：这几个是"集合 + 互斥值"，**交集恰好等于 AND**
  （`(传奇 或 史诗) 且 (史诗 或 稀有)` = 史诗）。⚠️ 交集为空时用一个数据库里
  不存在的哨兵值表达"必然没有结果"——后端把空数组理解为"不限"，不能用空数组。
  ⚠️ 职业两组逻辑不同时（一侧"与"、一侧"或"）后端表达不了，取并集 + "与"（只会更严）。

**「退出搜索」**：清空关键词 + 全部搜索条件，回到没搜过的列表。
★ 刻意**不动过滤器**——搜索与过滤是两套东西，过滤器有自己的「清除」。
它只在"正在搜索"时出现（搜索行里 / 专注模式右上角）。

## 6. 前端"按字符串上色"的全部位置（审阅用，2026-09-13）

用途：说清"哪些颜色是游戏给的、哪些是我们猜的"。想加/改着色规则时对着这一节看，
别漏了同一条链上的其他地方。

### 6.1 照游戏给的码渲染（不是猜）——主力

`parseRow()`（`ReplicaStatList.tsx`）：扫过 `^X` 就切成 `<span class="tt-X">`；
CSS（`ReplicaStatList.css`）里 `.tt-X` 那张表决定颜色。
行上另外挂 `.tt-type-N`（**行种**基础色）与 `.tt-indent-N`（缩进，不影响色）。

> 也就是说：**只要游戏给了码，颜色就是"游戏原样"**，前端不参与判断。

### 6.2 真正的"猜"——按字符串匹配**补**色，共 4 处（都在 `ReplicaStatList.tsx`）

| # | 函数 | 匹配什么 | 补成什么 |
|---|---|---|---|
| 1 | `colorizePlainSkillRow()` | 正则 `PLAIN_SKILL_ROW`：`<职业>技能名 (英文) 技能等级 +N` | `^g<^F职业^g>^c技能名 ^s(英文) ^E技能等级 ^H+N` |
|   |  | 正则 `PLAIN_ALL_SKILLS`：`职业 所有技能 +N` | `^F职业 ^c所有技能 ^H+N` |
| 2 | `normalizeBareClassMark()` | `^X` 紧跟的**职业名**（查职业表） | 补上尖括号 `^g<^F职业^g>` |
| 3 | `matchClassName()` / `findLineClass()` | **职业名**（查职业表） | 挂 `tt-cls-*` 职业色；尖括号跟着职业色走 |
| 4 | `parseRow()` 内部两处 | 文本正好是 `所有技能` | 固定 `tt-c` |
|   |  | `SKILL_ROW_CODES = {g, F, L}` 出现在**技能行**里 | 统一成 `tt-skill` |
| 5 | **`recolorStats()`**（`model/statColors.ts` + 生成物 `statColors.table.ts`） | **属性关键词**（124 条，伤害/抗性/反击/人物属性/速度…） | `^X关键词^-`——**覆盖**原有的码（"统一观感"的落点，见 §6.2 下文） |

⚠️ 第 4 条是"同一个码在不同语境语义不同"的补丁：`^F` 在属性行是**活力伤害**（桃红）、
在技能行却是**职业名**。所以只能按行判断。

#### 第 5 条那张表是怎么来的（★ 也是"统一观感"的落点）

★ **立场（使用者 2026-09-13 定）**：

> 不管玩家装了哪份汉化包、把它改成了什么颜色，**到我们这儿一律以本表为准**。

所以这张表不是"补漏"，而是**唯一标准**：渲染前会用它**覆盖** tooltip 里原有的
`^X` 码（含 `^H` 数值段）。同名属性在不同汉化包/不同条目里颜色不一致的问题，
到此为止。

**表在哪**：`model/statColors.table.ts` —— **我们自己的颜色风格表，手工维护**。
要加词、改色、删词，直接改它（使用者 2026-09-14 定：先拿现在这份用起来，后面慢慢修补）。

它最初是从工程自带的汉化包 `gd-tags-ui.zh.txt` 整理出来的
（B站 up 主「**发光的洛伦兹**」的 Grim Dawn 汉化包 `Text_ZH/tags_ui.txt`，
原样拷贝；**只作参考来源、不参与构建**）。整理时的判据：

★ **`^E` 是"默认属性色"，非 `^E` 才是作者特意配的。**

- 表的主体 = **非 `^E` 的词**（伤害 / 反击 / 人物属性 / 速度 / 眩晕时间…）——
  那批本来就干净，是作者的配色意图；
- `^E` 的词只留两类：开头那张"**颜色对应表**"里列出的（作者人工整理过的
  核心属性名），以及**以"抗性"结尾**的；
- **其余 `^E` 一律不要**：它们混着大量修饰语与句子片段（"减少""个目标"
  "度攻击范围""来自""受到"），收进来只会把原本无色的文本染成棕色；

#### 为什么不从 tag 代码反推中文（使用者 2026-09-13 问过）

汉化包里是这么一条：

```
tagDamageModifierCritDamage={%+.0f0}% {^H}暴击(Crit)伤害
        ↑ tag 名                              ↑ 中文文本
```

看着很自然的一条路：运行时不匹配文本，而是**记住 tag → 查中文**。
**走不通**，三个原因：

1. **游戏导出的 tooltip 行里没有 tag。**
   `replicaStats` 只有 `Type`（行种编号）+ `Text`（**渲染后的**文本）。
   库表结构就是 `ReplicaItemRow(Id, replicaitemid, Type, Text, TextLowercase)`
   —— 没有 tag 列。tag 在游戏渲染成文本的那一刻就丢了。
2. IA 另一条数据（`DatabaseItemStat_v2` 的 stat 字段名，如 `offensiveCritDamage`）
   只覆盖**物品的基础属性**，与 tooltip 行不是一对一（tooltip 里还有套装、
   授予技能、伤害转换那些），而且 IA 用它拼出来的 `headerStats` **实测全空**。
3. 要真拿到 tag，得改**游戏内的 hook**（C++），在导出 tooltip 时把 tag 一并带上——
   那要摸游戏版本的内部结构，风险和工作量都不成比例。

所以只剩"**文本匹配**"这一条路；表要做得**小而准**（124 条）就是这个原因。

> 汉化包里的 tag 名仍然有用——**离线**看它能发现"同一个中文在哪些 tag 下出现、
> 颜色是否一致"（比如 `暴击` 与 `暴击(Crit)伤害` 是两条不同的模板）。
> 但**运行时**用不上。

> **i18n 不做**（使用者 2026-09-13 定）：只考虑中文。所以**没有英文词表**。
> 真要支持英文，再照同一套路加一张英文表。

### 6.3 按"形状"判断行的角色（影响色，但不是码匹配）

- `isSkillRow()`：`text.includes('技能等级') || text.includes('^g<')`
- `skillRowKind()`：句号结尾 → 说明；含 `施放该技能`、或**行首**是 `<职业>` 标记 → 名字；其余 → 参数
  （`<职业>` 必须在行首：`造成暴击时有 25% 几率触发<爆破>手榴弹…` 这种触发效果行
  虽然含职业标记，但它是**参数行**）
- `indentLevels()`：主要按 `type` 分档；`type 82` 用上面的形状兜底（见 §1.4）

### 6.4 物品名那条链（另一处，独立于 tooltip）

- `ItemName.tsx` → `parseRow(composeItemName(item).name)`
- `composeItemName()`（`model/affixes.ts`）：**词缀**文本来自词缀表 `affixes.json`
  （503 条，自带 `^y` / `^g`）；**基底名**的颜色码是**从游戏名字行里抠出最后一个 `^X`**
  （`/^[a-zA-Z-]/g`），不自己定色

### 6.5 品质色（不是 tooltip，但也靠一张表）

- `ItemCard/quality.ts` 的 `ALIASES`：`Epic → quality-legendary`、`Blue → quality-epic`…
  （那对交叉命名，见文件顶部注释）

### 6.7 重新着色的**范围按行种收窄**

★ 一开始是"整行都过一遍 `recolorStats`"，结果**一刀切出两个误伤**
（使用者 2026-09-13 报的）：

| 行 | 文本 | 误染 |
|---|---|---|
| `type 37`（技能名） | `伊斯坎德拉的元素撕裂(造成暴击时有 30% 的几率施放该技能)` | "**暴击**"是描述短语，被染成金色 |
| `type 22`（套装说明） | `…"万用对戒，生命恢复（神话级与普通的混搭不能取得套装效果）` | 说明里的"**生命**"被染成桃红 |

→ 所以**只对"属性内容行"重新着色**（`RECOLOR_TYPES`）：

- **收**：`18`（基础数值）、`19`（普通属性）、`20`（每秒攻击 / 需求）、`26`（技能下辖属性）、
  `28`（套装加成）、`33·42·55·69·71`（组件 / 战宠下属属性）、`79`（`+2 到某技能`）、
  `83`（授予技能参数），以及 **`type 82` 的参数行**
- **不收**：物品名 `7`、类型 `66`、flavor `16·17`、套装名 `21`、**套装说明 `22`**、
  成员与层级 `23`、段标题 `24·25·34·36·65·67·68·70`、**技能名 `37·38·53`**、
  技能描述 `39·40`、授予技能抬头 `81`，以及 **`type 82` 的名字与说明**

`type 82` 同时装着"技能名 / 说明 / 参数"三种东西，靠 `skillRowKind()` 再分一次——
**只有参数行**重新着色。

`skillRowKind()` 认的三种形态（实测数据一条条对出来的）：

| 形态 | 例子 | 判定 |
|---|---|---|
| 带 `(…施放该技能)`，或**行首**是 `<职业>` 标记 | `伊斯坎德拉的天之裂片(攻击时有 15% 的几率施放该技能)`、`<士兵>佐尔汉的技艺` | 技能名 |
| 以句号结尾 | `复仇者的精神在你体内膨胀。` | 说明 |
| **干干净净一行纯中文**（无颜色码、无数字、≤12 字） | `命运封印` | 技能名 |
| 其余 | `5 ^E秒^E技能冷却时间`、`+8% ^H攻击能力(OA)` | 参数（米黄） |

> ⚠️ 第三种是 2026-09-14 补的：使用者报「复仇之拳 → **命运封印**没被识别成技能名」——
> 它既没有括号也没有句号，之前被当成参数。敢用"无码无数字"来判，是因为参数行
> 几乎总带数字或颜色码。

> ⚠️ 第一行的 `<职业>` **限定在行首**（2026-09-14 使用者报的另一处误判）：
> 「神话 撒旦」上那两条触发效果
> `造成暴击时有 25% 几率触发<爆破>手榴弹 (Grenado) 冷却时间减少 2 秒`
> 也含 `<职业>`，但它们其实是**参数行**，被错判成技能名后颜色/字重都跟着技能名走，
> 和同一块里的其它参数不一致。纯技能名去掉颜色码后**一定以 `<` 开头**，据此区分。

> 教训：字符串匹配的**作用域**要和"这行是干什么的"对齐。全局匹配省事，
> 但会去染说明文字和技能名里的同名词。

### 6.8 表外的东西会怎样（预期行为）

- 表里没有的属性词：**保持原样**（有码就还是那个码，没码就还是默认色）。
  这是刻意的——宁可不动，也不猜。加词就往 `TABLE` 里加一行。
- `^s`（英文技能名）、`^c`（技能名）、`^g`/`^F`（职业标记）、`^w`（名字白）、
  `^r`（需求）等**非属性语义码**不受影响：它们不在"属性词"的管辖范围内。
