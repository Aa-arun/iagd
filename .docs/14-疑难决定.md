## 1. 高级搜索的图标：自绘

**问题**：使用者给了参考 <https://www.grimtools.com/db/zh/> 的 `id="btn-adv-search"`，并说"直接画还是参考由你决定"。

**查到**：该站被 Cloudflare 挡着——直接抓返回 403，经本机代理（`10808`）再抓仍是 403，拿不到那个按钮的图标。

**决定**：自绘一个内联 SVG：三条带滑块的横杆（"精细调节"的通用符号），颜色用 `currentColor` 跟随主题。

**为什么**：项目不引 CSS 框架、也还没引图标库；为一个按钮添一个图标依赖不划算。而这个符号本身就是通用语义，不需要照抄某个站。

## 2. 品质多选与"1 / 2 个绿色词缀"不兼容

**问题**：`GET /api/filters/options` 的 `qualities` 里 `Green` 出现三次（`prefixRarity` = 0 / 1 / 2，对应旧界面的"稀有 / 1 绿色词缀 / 2 绿色词缀"）。但品质多选走的是 `rarities` **数组**，而 `prefixRarity` 是**单值**——两者没法同时表达。

**决定**：面板里的品质**按值去重**，只留 4 个：魔法 / 稀有 / 史诗 / 传奇。绿色词缀细分**不做**。

**为什么**：checklist 的语义是"这些都要"，而词缀数量是"至少几个"的阈值语义；混在一起会得到"稀有（不限词缀）OR 1 个词缀"这种没有意义的结果。旧界面那个细分是**单选**用途，放进多选面板只会误导。

> 后端字段都还在。将来真要这个细分，应该做成一个独立的阈值控件（"绿色词缀 ≥ n"），而不是品质选项。

## 3. 死代码清理的边界

**问题**：审计出几十个"零引用"的类型，但"零引用"不等于"该删"。

**判据**：**删掉之后会不会有人回来找它。**
- 逻辑**已被取代**（搬到了新地方）或**功能已明确不做**（图鉴）→ 删。
- 只是**暂时没有入口**、但将来要用的实现 → 留。

**按这条线分的结果**：

| 处理 | 内容 | 理由 |
|---|---|---|
| 删 | `UI/Filters/`、`UI/DesiredSkills.*`、`Theme/Firefox/`、`NumericFilterDialog`、`SettingsController` 三件套 | 定义已搬进 `Services/Filters/FilterCatalog.cs`，能力不丢；界面本身已由网页取代 |
| 删 | 图鉴残留（`IItemCollectionDao` / `ItemCollectionDaoImpl` / 两个 Model） | 图鉴页已决定不做 |
| 删 | `SearchController` 的 WebView2 推送通路、`ItemPaginationService`、各事件残留类 | 接收方（旧 Preact 前端）已不存在 |
| **留** | `UI/Popups/ImportExport/`（导入导出**物品**，无入口） | 它是"备份恢复"的**现成实现**，而使用者只是决定**暂缓**那个功能（`11-备份与恢复.md`）。删了要去 git 历史里翻 |
| **留** | `IBrowserCallbacks` 的接口名与 `UI/Misc/CEF/` 位置 | 它还剩两个活方法，且同目录的 `IUserFeedbackHandler` 仍在用。改名要把改动扩散到三个文件，换来的只是"名字好看" |

**顺带结论**：`UI/Misc/CEF/` 这个目录名（CEF = 已删掉的 Chromium 内嵌框架）确实已经名不副实，但它装的东西还在用——留着，等哪天整块都不用了再一起清。

## 4. `headerStats` 全为空：有意抑制，不修

**问题**：`.docs/08-属性翻译.md` 与 `00` 的待办里都记着"`headerStats` 实测全为空，值得查是不是解析侧的问题"。

**查到**：**不是解析问题，是有意的抑制**。
`ItemHtmlWriter.cs:107` 有一句 `skipStats = replicaStats != null`，`:133` 据此把 `HeaderStats`（以及 `PetStats`）置空——因为 IA 采集物品时**游戏已经把完整 tooltip 给过来了**（`replicaStats`），再拿数据库重拼一份只会重复渲染。上游数据其实齐全（`ItemStatService.BuildTags` 已把护甲、生命等填好）。

**决定**：**不修**，从待办里去掉。

**为什么**：这不是缺陷。真正要解决的是另一个问题——"列表里想显示关键属性（护甲/生命）时没有结构化的数值可用"。那应该**在 `ItemHtmlWriter` 里另出一组白名单字段**（或让前端复用已经算好的 `ComputedItemStat`），而**不是**放开那句 `skipStats`——放开只会让详情面板把同一件装备的属性渲染两遍。

> 所以 `00` 里那条待办的正确形态是"列表要不要显示关键属性列"，而不是"headerStats 为什么空"。

## 5. 属性翻译的"前缀变体"缺口：成立，已修

**问题**：属性翻译的规则是"stat 名就是模板 key"。但 `08-属性翻译.md` §5.2 记着一个缺口：有些属性的模板 key 带前缀，例如 `skillManaCostReduction` 的模板其实叫 `customtag_xpac_modif_skillManaCostReduction`。那条记录是针对**已退役的 Node 原型**写的，C# 侧从未验证。

**查到**：**缺口在 C# 侧同样成立**，但成因和当初猜的不一样——
C# 的 `MapSimpleBodyEntries` 是"**白名单**循环 + 同名 `GetTag`"，**没有兜底遍历**：取不到模板就返回空串，属性被静默丢掉。`skillManaCostReduction` 恰好既不在白名单里、也没有同名模板。

**决定**：修。给白名单补上该项，并加一层兜底：同名取不到时再试 `customtag_xpac_modif_<stat>`；同时**过滤掉最终仍取不到模板的项**（否则会渲染出一条空属性）。

**顺带修了一个真 bug**：`StatManager.cs` 里"减少目标伤害"和"降低目标抗性"两个分支的模板**用反了**（对照 `EnglishLanguage.cs:219-220` 可确认）。这个不是缺口，是写错了。

## 6. 后端剩余项的价值判断：三项不做

`13-后端待办与计划.md` §2.2 里有几项，做完调研后判断**不值得做**——理由记在这里，免得下次又翻出来重议。

| 项 | 判断 | 理由 |
|---|---|---|
| **WebSocket 广播盲区**（改动已有物品不触发 `itemsChanged`） | 不做 | 真实场景只有"更新项目统计"，而它**走维护模式**——维护结束时 `WebServer.ExitMaintenance` 已经广播过了。其余触发点要靠后台线程跨服务接线，收益对不上 |
| **预计算滞后**（刚拾取的物品要等后台算完才能被数值过滤查到） | 不做 | 后台每 2.5 秒推进 25 件，窗口很短；要消除它得让拾取路径直接调用预计算并广播，跨三条链路 |
| **`/api/filters/options` 加缓存** | 不做 | **实测 30 ms**（本机 66 件物品）。低频调用，缓存带来的失效问题比省下的时间值钱 |

## 8. 过滤器的两种逻辑：颜色即语义（2026-09-13）

**问题**：使用者要求物品属性"默认与逻辑，点击后变成或逻辑"，而品质与槽位"一直是或逻辑"。
同一个面板里于是有**两种逻辑**，怎么表达、又在哪里切换？

**决定**：**颜色即逻辑** —— 黄 = **与**（同时满足），绿 = **或**（满足任意一个）。

| 谁 | 怎么切换 |
|---|---|
| **物品属性的四个分组**（伤害 / 持续伤害 / 抗性 / 杂项）**与职业** | 逻辑是**组**的属性：点**组名**在"与 ↔ 或"之间切换，组名本身显示黄/绿；组里的选项只有选中/未选两态，**颜色跟随组** |
| 品质 / 槽位 | 不切换——它们天生是"或"（选了传奇和史诗当然是两个都想看到），选中即**绿** |
| 开关类（已镶嵌、战宠…） | 不切换——各自是独立布尔、彼此只能"与"，选中即**黄** |
| **槽位那四组**（护甲 / 武器 / 首饰 / 物品） | 组名是这个筛选器的**快捷全选**（没全选→全选，全选→全清），与逻辑无关 |

**为什么逻辑放在组上而不是每个选项上**：使用者的原话是"点击『直接伤害』这种组名的时候，
颜色会切换……后面的 chip 之间的逻辑改为与/或"。同一组里的属性本来就该用同一个逻辑
（想的是"火焰**且**冰冷"或"火焰**或**冰冷"，不会是"火焰且冰冷或闪电"）。
组级切换符合直觉，也省掉了每个选项一个开关。

**物品属性那一侧后端不需要改**：`ItemSearchRequest.Filters` 本来就是"**组间与、组内或**"
（`List<string[]>`）。所以"与"的组里每个被选选项各占一组，"或"的组里所有被选选项合并成同一组。

⚠️ **职业那一侧要改**：它原来是"每个职业一条子查询"，天然只有"与"。
所以加了 `ClassesAny`：true 时合并成一条 `dbs.stat IN (加成字段) AND dbs.TextValue IN (:classAny)`。
实测 class02+class03：**与** = 4 件（同时加成这两个职业），**或** = 34 件。

**图例**：面板展开时右上角有一行"与 / 或"的说明，否则颜色的含义要靠猜。

## 9. "双稀有"逼出一个后端字段

**问题**：使用者要"品质增加一个**双稀有**，用来筛选『萨拉查的王者之剑』这种双稀有装备"。
但品质多选走 `rarities: string[]`，而"双稀有"= 品质 `Green` **且** 词缀数 ≥ 2 ——
`prefixRarity` 是**单值**字段，与多选不兼容（§2 已经因为同一原因砍掉过"1/2 个绿色词缀"）。

**决定**：后端新增 `RarityConditions: [{ rarity, prefixRarity }]`，**组内是或**；
前端品质的 key 用"值:词缀数"（`Green:2`）来区分"稀有"与"双稀有"。

**为什么不在前端特判**：特判只能表达"双稀有"这一个组合。将来还想要"稀有且 1 个词缀"、
"双稀有 **或** 传奇"时，前端拼语义就会失控。把"品质 + 词缀数"做成后端认识的一条条件，
剩下的组合是免费的。

**实测**：`[{Green,2}]` → 1 件，正是「崩碎现实之 幽灵束缚的 萨拉查的王者之剑」；
`[{Green,2},{Epic,0}]` → 41 件 = 1 + 40（或逻辑成立）。

## 10. "所有物品"用反选，而不是列一张清单

**问题**：使用者要物品组里加"所有物品"，"用反选的方式筛出除了装备外的所有物品，
防止我的分类有遗漏"。

**决定**：它不是某个槽位，而是**排除全部装备槽位**（`slotInverse` + 护甲/武器/首饰三组的 key）。
选中它与逐项选择**互斥**。

**为什么**：槽位清单是**我按使用者的分类整理的**——将来漏了哪一类，"所有物品"仍然能捞出来。
反过来列一张"非装备槽位"清单就做不到：那又变成"我的分类"，兜不住自己的遗漏。

## 12. 槽位与职业清单硬编码在后端

**问题**：使用者逐项给了槽位的分组、顺序与改名（护肩/护手/护腿/靴子/单手远程/双手矛…），
以及十个基础职业的顺序与名称。这些放哪？

**决定**：放后端 `FilterCatalog`（`SlotGroups` / `BaseClasses`），**前端只渲染后端给的东西**。

**为什么**：
- 顺序与命名是**使用者的选择**——既不是游戏数据的顺序，也不是翻译表能推导出来的。
- i18n 表里那些 `iatag_slot_*` 同时还给**物品列表的"槽位"列**用，所以那几处改名照改
  （列表也该显示"护肩"）；但"怎么分组、谁先谁后"在翻译表里没有位置。
- 硬编码在 `FilterCatalog` 还让"哪几个槽位算装备"只有**一个来源**——
  §10 的反选正好要用这份清单。
- 去掉了游戏数据里的**组合职业**（`class0102` = 士兵+爆破）：装备上的职业加成只针对单个职业。
  另外 `class07/08/09` 在游戏数据里是 `?`（缺翻译），硬编码名称正好绕开。

## 13. 高级搜索为什么把条目又列了一遍

**问题**：高级搜索做成模态后，里面的条目与过滤面板**大量重复**（类型、稀有度、职业、物品属性），
为什么？

**决定**：重复，但**共享同一份状态**——在模态里勾"火焰"，面板上也亮着。

**为什么**：
- grimtools 的高级搜索就是一个**完整**的筛选面板，使用者要的也是这个
  （"根据我们筛选器中有的条目…弄一个初版"）。
- 只把"面板没有的"（等级、属性数值、入库时间、排序）放进模态，会让"想在一个地方把条件看全"
  这件事无处可去。
- 共享状态意味着**不存在两套条件**：模态只是同一份数据的另一种排布。

**代价**：`components/Filters/chips.tsx` 必须抽出来给两边共用——那正是它存在的原因。

## 14. 高级搜索改"草稿态"（2026-09-13）

**问题**：高级搜索原来是**实时共用**过滤面板的状态——在模态里点一个色块，背后的列表立刻变了。
使用者要求改成："高级搜索中的这些选项应该只用于筛选最终搜索的结果，而非实时影响当前显示的内容"。

**决定**：高级搜索打开时，把当前条件**复制成一份草稿**；模态里怎么改都只动草稿；
点「完成」才整体写回主状态并触发查询；「取消」/×/Esc **丢弃**草稿。
顶部也补上自己的搜索框，**关键词同样走草稿**。

**为什么**：

- 高级搜索是"一组条件一次性想清楚再执行"的工具，实时预览反而让人不敢点
  （每点一下列表都在跳，还会把当前的浏览位置冲掉）。
- 过滤面板本来就是"边点边看"的快速条——两种节奏不一样，所以**不强行统一**：
  面板实时、高级搜索草稿。

**实现**：`views/useFilters.ts` 拆成两层——`useFilterState(initial)`（纯状态 + 操作，不落盘）
与 `useFilters()`（主状态 + localStorage）。草稿就是前者的第二个实例。两处共用同一份操作实现，
所以语义不会漂移。

**代价**：`chips.tsx` 现在接收的是"一套状态 + 操作"而不是全局单例；`AdvancedSearch` 的
props 多了一层"草稿 → 主状态"的提交。

> ⚠️ 使用者原话里还有一句"高级搜索不和过滤器共用 `filter-chip`"。这里按**状态独立**理解并落地：
> 高级搜索仍然复用同一批色块组件（观感一致），但**不再是同一份实时状态**。
> 若将来要的是"连样子都不同"，改的是 `chips.tsx` 的样式变体，不是状态层。

### ★ 同一天的修正：草稿写回的是**搜索条件**，不是过滤器

上面那版把"草稿"写回**过滤器**（点完「完成」，过滤面板就跟着亮起来）。使用者随后澄清：
**这不对**——高级搜索的选项是"搜索条件"，不该改动过滤器。详见 §18。

## 15. 排序：四级次序与"品质值交叉"（2026-09-13）

**问题**：排序原本是高级搜索里的一对单选（按名称 / 按等级），使用者要求搬到工具条，
并给出明确次序。

**决定**：

| 选项 | 次序 | 说明 |
|---|---|---|
| 入库时间 | 入库时间（新 → 旧） | **默认**（不选任何排序时也是它） |
| 品质 | 品质 → 等级 → 名称 | 选中它，品质优先级最高，不再看入库时间 |
| 等级 | 等级 → 品质 → 名称 | 等级优先级最高 |
| 名称 | 名称 → 品质 → 等级 | 名称优先级最高 |

**为什么**：

- 排序是"怎么看"，不是"看什么"：放在高级搜索里每次都要开模态改一次，太绕；
  它也不该被"清除过滤条件"清掉，更不该计入"已选 N 项"。
- 所以它跟前端**视图偏好**同类（`views/useSort.ts` + localStorage），
  请求里只是一个 `sortBy` 字符串。

**两个坑**：

1. **品质不能按字符串排**。库里的值是 `Epic` / `Blue` / `Green` / `Yellow`，
   而上游命名是**交叉**的（`Epic` = 游戏里的传奇、`Blue` = 史诗，见 `ItemCard/quality.ts`）。
   所以 SQL 里用 `CASE PI.Rarity WHEN 'Epic' THEN 0 …` 映射成权重再排。
2. **必须由后端排**。分页是 `LIMIT/OFFSET` 切片，前端重排只会让"第几页"对不上；
   因此新前端**不再走 `/api/items`**，一律 `POST /api/search` 带上 `sortBy`。

**每条排序都以 `PI.Id` 收尾**：没有全序的话，同一件物品可能在两页里都出现、或者被跳过。

## 16. 字体与快捷键为什么放 localStorage，而不是 `settings.json`（2026-09-13）

**问题**：设置里要能改「详细对照 / 固定栏详情」的字体与字号倍率，以及 `f/s/i` 快捷键。
这些该存哪儿？

**决定**：存**浏览器 localStorage**（`prefs/UiPrefs.tsx` 的 Context），不进 C# 的 `settings.json`。

**为什么**：

- 它们**纯粹是浏览器这边的观感**：后端既不读、也不用。
- 进 `settings.json` 意味着改一次 C# DTO + `SettingsService` + 序列化 + 前端类型，
  收益是零。而现有后端设置项（隐藏技能、仓库、备份目录）都是**后端真的会执行**的东西。
- 与 `iagd.filters` / `iagd.sortBy` / `iagd.view` 是同一类偏好，放一起才一致。

**代价**：换浏览器 / 清缓存会丢。可以接受（它们本来就不影响数据）。

**实现细节**：字体写成 CSS 变量（`--compare-font-*` / `--detail-font-*`），
换字体只改 `document.documentElement` 上的自定义属性；
快捷键入一个 Context，因为**设置页要改它、AppShell 要读它**，分散成两个 hook 就没法同步。

## 17. 专注模式：为什么是"不渲染"而不是"隐藏"（2026-09-13）

**问题**：使用者要一个"整页都是 `app__content`"的专注模式（快捷键 `i`），
并且 `s` 仍能弹高级搜索、`f` 弹出"过滤器 + 视图工具条"。

**决定**：专注模式下 header / 页签 / 搜索行 / 工具条 / 过滤面板**直接不渲染**
（`!focusMode && …`），而不是用 CSS `display: none` 藏起来。

**为什么**：

- 少一层"看得见但点不到"的状态。藏起来的输入框仍可能被快捷键聚焦（`/` 会聚焦到不可见的
  搜索框上），那是很难查的怪行为。
- 不渲染就没有"专注模式下还在后台跑的下拉 / 弹层"。

**代价**：专注模式下要改视图 / 过滤，必须先按 `f` 打开 `FilterDialog`（那正是使用者要的交互）。
工具条组件在专注模式下由 `FilterDialog` 渲染，普通模式下由 `AppShell` 的工具栏渲染，**同一份组件**。

**另一个小决定**：专注模式下 `/` 打开**高级搜索**（它的顶部就是搜索框），
因为主界面那个搜索框此时不存在。

## 18. 高级搜索是"搜索条件"，不是"过滤器"（2026-09-13 使用者澄清）

**问题**：§14 把高级搜索做成了"过滤器的另一种排布"（草稿写回过滤器、过滤面板跟着亮）。
使用者指出这不对，并给了心智模型：

> 高级搜索里的选项**不是过滤器**。勾"穿刺伤害"就等于搜「某某装备 AND 穿刺伤害」，
> 它只决定**搜出来什么**；搜到的结果，你可以再用过滤器去筛。
> 就像搜名字一样。点「完成」不该改动过滤器的配置。

**决定**：拆成**两套独立状态**，请求里合并：

- `useSearchConditions()` —— 搜索条件（高级搜索弹窗，草稿态）。
- `useFilters()` —— 过滤器（过滤面板，实时）。

结果 = 搜索（关键词 + 高级搜索条件）**AND** 过滤器。合并细节见
[`12-装备显示与交互.md`](./12-装备显示与交互.md) §4.8。

另加一个「**退出搜索**」按钮：清空关键词 + 全部搜索条件，回到没搜过的列表。
**刻意不动过滤器**——过滤器有自己的「清除」。

**为什么值得为它拆两套状态**：

- 两者**生命周期不同**：搜索是"这一轮想看什么"（常用「退出搜索」整体丢掉），
  过滤器是"我长期只关心这些"（比如只玩传奇装备，会一直挂着）。
  混成一份的话，"退出搜索"就得猜要不要连过滤器一起清。
- 两者**可见性不同**：过滤器在主界面上一直看得见（折叠头 + 角标），
  搜索条件藏在模态里（按钮角标 + 「退出搜索」按钮提示它还在生效）。
- 后端只认一个请求体，所以合并点是 `buildSearchRequest` 一处——那是唯一需要小心的地方。

**代价 / 已知近似**：品质、槽位、职业这三个"集合类"字段两边都设时，前端做**交集**
（对互斥值来说交集 = AND）；职业两组逻辑不同（与 / 或）时取并集 + "与"，
只会更严不会更松。详见 §4.8。

## 19. 快捷键冲突：两项互换，而不是拒绝（2026-09-13）

**问题**：四个快捷键（搜索框 `/`、过滤器 `f`、高级搜索 `s`、专注模式 `i`）
原先可以设成同一个键——按一下会触发两件事。

**决定**：在设置里改键时，如果这个键**已被另一个功能占用**，两项**互换**。

**为什么不是"拒绝并提示"**：键位总数是固定的，想把 `git` 式的键腾出来通常就是
"我想换到那个键上"，交换一步到位；拒绝的话用户还得先去把对方改成别的，
再回来改这个——两步，而且中间态可能又撞上。

**另一个决定**：`c`（清除过滤条件）是**固定键**，不参与改键，且它的判断放在
**所有自定义快捷键之后**——万一有人把某功能设成 `c`，那个功能优先。

## 21. 套装授予技能：整块都是 `type 82`，只能按文本形状分角色（2026-09-13）

**问题**：使用者报"套装里授予的技能，名字和说明都是黄色的"（正常授予技能区是
名字蓝、说明灰）。

**根因**：游戏导出 tooltip 时——

| 区块 | 技能名 | 说明 | 参数 |
|---|---|---|---|
| 普通授予技能 | `type 37` | `type 39` | `type 81` 抬头 + `82` / `83` |
| **套装授予技能** | **`type 82`** | **`type 82`** | `type 82` / `83` |

套装那一块**没有 `37` / `39`**，整个技能（名字、说明、参数）都是 `82`。
而 CSS 里 `.tt-type-82` 是"技能参数"的米黄，于是名字和说明都被涂成了黄。

**决定**：在 `ReplicaStatList.tsx` 里加 `skillRowKind(text)`，按**文本形状**判断：

- 以句号结尾、且不含数值色 `^H` → **说明**（`.tt-skill-desc`，灰）
- 含 `(…施放该技能)` 括号、或带 `<职业>` 标记 → **名字**（`.tt-skill-name`，蓝）
- 其余 → 参数（保持米黄）

**为什么用文本形状而不是再加一张 type 表**：同一件装备上，"名字"和"参数"的
`type` 完全一样，type 里没有信息可用；而形状在实测数据里很干净
（对照「复仇粉碎者」「伊斯坎德拉的文本」两块，每行都对得上）。
缩进也顺带用它兜底：套装区的参数行原先因为没有 `type 81` 抬头而少缩进一级。

**代价**：如果将来某件装备的说明不带句号、或技能名不带括号，会退化成"参数"——
只是颜色偏米黄，不会显示错内容。宁可保守。

## 22. tooltip 配色：**以工程自带的表为唯一标准，渲染前覆盖**（2026-09-13·14）

**问题**：套装加成那些行（`+120% 酸性伤害`、`+4% 攻击能力(OA)`…）在游戏导出时
**没有 `^X` 颜色码**，而中间夹着"技能等级 +3"这类会被前端补色的行 → 整块"部分白、部分花"。

**查清的两件事**（都推翻了中途的假设）：

1. **颜色码是汉化包加的**，不是游戏引擎给的——tooltip 里每个码都能在汉化包里找到出处
   （`DamagePoison={%t0} {^G}酸性伤害{^-}`）。所谓"套装加成无码"，是作者没给那些条目加色。
2. **两份汉化包在"活力 / 混乱"上配色相反**，各自内部都自洽 →
   只要"照游戏给的渲染"，装不同包的人看到的颜色就必然不同。

**决定**（使用者原话："*不管他打了什么乱七八糟的汉化包，改了什么乱七八糟的颜色，
到我们这儿一律以我们这个软件显示为准*"）：

- 表以工程自带的 `gd-tags-ui.zh.txt` 为**唯一标准**，整理成**手工维护**的
  `src/model/statColors.table.ts`（160 条）；
- 渲染前**重新着色**：表里的属性词一律换成表里的码——**覆盖**游戏给的（含 `^H` 数值段）；
- ⚠️ **作用范围按行种收窄**：只碰"属性内容行"（`18/19/20/26/28/33/42/55/69/71/79/83`
  与 `type 82` 的参数行），名字 / 说明 / 标题一律不动
  （否则技能名里的"暴击"、套装说明里的"生命"都会被误染）；
- **i18n 不做**，所以没有英文表。

**关键判据**（绕了三版才定下来）：

> **`^E` 是"默认属性色"，非 `^E` 才是作者特意配的。**

表的主体取**非 `^E`** 的词；`^E` 里只留两类——文件开头那张"颜色对应表"里列出的、
以及以"抗性"结尾的。

**自定义码**：使用者定"**配色表里的码是我们自己的**，可以自己造"——
目前 `^Q` = 混乱（游戏里"混乱"和"体格"共用 `^O`，颜色分不开，于是单开一个码；
`^O` 留给体格 / 所有类型伤害 / 最大全抗性）。

**走向行种优先**：同一个码在不同行种里含义不同（`^o` 在套装说明里是"注记"、
在镶嵌物名字里是"标题"），**冲突时行种优先**——所以码**默认中性**（`inherit`），
只在明确的行种里显式给色；别给码"默认色"，那会逼着每个冲突点去打补丁。

> **完整细节**（判据怎么来的、三段弯路、行种清单、自定义码约定、分色表）→
> [`12-装备显示与交互.md`](./12-装备显示与交互.md) §1.3、§6。

## 23. 「详情」到底有几种：为什么**按视图**给不同的选项（2026-09-14）

**问题**：0914 todo 里，"分栏列表"和"简洁卡片"两节都写了"详情 - 浮动 删去，
只留左侧固定栏/右侧固定栏"，但"简洁卡片"那节后面又详细描述了浮动面板的定位
需求——到底删不删？

**追问后的答复**（使用者）："视图 - 分栏列表 / 简洁卡片 **采用不同的选项**。"

**决定**：

| 视图 | 「详情」可选 | 为什么 |
|---|---|---|
| 分栏列表 | 左 / 右固定栏 | 表格是逐行扫视的，浮动面板跟在鼠标旁边会一直挡住相邻的行 |
| 简洁卡片 | 浮动 / 左 / 右固定栏 | 网格里卡片大小不一、留白多，浮动预览正好合适 |
| 详细对照 | 无 | 它自己就把完整属性摊开了 |

**实现上的两个要点**：

1. 允许哪些方式写在**视图注册表**里（`ItemViewDefinition.detailModes`），
   不是工具栏里写 `if (viewId === 'table')`——将来加视图只加一行。
2. 存下来的偏好不被当前视图支持时**收敛到该视图的第一个选项，但不写回存储**。
   于是"简洁卡片选了浮动 → 切到分栏列表（自动变右固定栏）→ 切回简洁卡片"
   仍然是浮动，两个视图互不干扰。收敛点是 `effectiveDetailMode()`，由
   `ItemDetailProvider` 统一执行——这样"面板行为"与"对外报告的模式"永远一致，
   不会出现"模式是浮动、行为却按固定栏（不保留 hover 内容）"这种自相矛盾。

> ⚠️ 一个容易踩的细节：`onItemHover` 里"固定栏模式不清空内容"的判断必须用
> **收敛后**的模式。早先用的是存下来的原值，分栏列表若留着"浮动"偏好，
> 鼠标一移开内容就没了——看起来像面板抽风。

> 相关：浮动面板的定位（另一侧 + 中线对齐）→ [`12-装备显示与交互.md`](./12-装备显示与交互.md) §4.1。
